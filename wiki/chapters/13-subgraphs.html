子图与多 Agent：先隔离上下文

源码快照 2026-09-22 · 约 10 分钟

多 Agent 不是“多创建几个模型”这么简单。每增加一个 Agent，就增加一套提示、工具、消息历史、失败模式和观测路径。子图的首要价值是边界，不是角色扮演。

先问为什么要拆#

适合拆成子图的信号：

  • 某段流程有独立状态与完成条件；
  • 需要单独测试、重试或复用；
  • 工具权限与其他步骤明显不同；
  • 上下文很大，但只应让某个专家看到；
  • 团队或部署生命周期不同。

“让系统看起来更智能”不是理由。一个 Agent 加两个确定性工具往往比三个互相聊天的 Agent 更可靠。

子图的两种数据边界#

共享 state key#

父图与子图使用部分同名字段，子图可直接作为节点加入。适合紧密协作，但要清楚 reducer 和 checkpoint namespace。

显式输入输出转换#

父节点调用子图前构造窄输入，完成后把结果映射回父 state。代码多一点，却能阻止上下文泄漏和字段偶合。

父图完整 state
    │  select: question + approved_sources
    ▼
研究子图
    │  return: findings + citations
    ▼
父图只合并公开结果

涉及权限、隐私或不同业务域时，优先显式转换。

专家不需要看到主流程的全部历史#

研究子图需要问题和允许引用的材料，不需要用户支付凭据或发布工具。父节点显式选择输入，子图返回 findings 与 citations，父图再合并公开结果。这样即使专家提示被材料干扰，也没有自动获得主图全部能力。

共享字段方便少写映射，却让 reducer、字段含义和持久化边界更紧密耦合。两个子图都写 messages 时，还要判断这些消息是否应该进入同一对话。接口短不是唯一目标，窄上下文通常更容易核验。

常见多 Agent 模式#

Router#

一个路由步骤选择专家，适合问题类型互斥的场景。路由最好使用结构化输出，并提供 unknown/fallback 分支。

Subagents#

主 Agent 把窄任务交给子 Agent，再汇总结果。主 Agent 不必把全部会话和全部工具复制给每个子 Agent。

Handoff#

当前 Agent 把控制权和必要状态交给另一个 Agent。handoff 是状态机转移，不只是生成“请转给财务”文本。

Custom workflow#

确定性节点、Agent 子图、审批和并行任务混合。生产系统通常属于这一类，而不是纯粹的 Agent 对话网络。

Context engineering 比角色描述重要#

“你是研究专家”对行为有帮助，但下面这些更决定质量：

  • 输入里只放与任务相关的资料；
  • 只注册该角色允许使用的工具；
  • 给出明确输出 schema；
  • 限制时间、步数和费用；
  • 指定无法判断时的升级路径；
  • 将可信业务事实与用户文本分离。

多 Agent 的优势常来自上下文隔离，而不是并行调用更多模型。

多个角色的多数意见不是独立证据#

三个专家读同一份错误文档，可能一致给出错误答案。聚合时应检查引用、来源依赖和具体分歧，而非仅数赞成票。不同角色 prompt 改变阅读侧重点，没有自动增加三份独立事实。

如果某专家发现缺少批准人资料，另一个给出人名，主图应核对来源，不把表达自信当作证据。子任务返回结构化结果和未知原因，比长篇互相对话更容易让聚合节点做可靠选择。

记忆放在哪一层#

  • 子图内部临时推理：子图 state。
  • 父流程需要的结果：映射回父 state。
  • 同一 thread 的恢复：checkpointer。
  • 跨 thread 的用户或组织知识：store。

如果每个子 Agent 都保存一份完整对话，状态体积和一致性问题会迅速增长。尽量传递摘要、引用和稳定对象 ID。

并行专家与聚合#

并行适合彼此独立的任务，例如从源码、文档和测试三个角度收集证据。聚合节点应显式处理冲突，而不是简单拼接所有结论。

一个证据对象至少包含：

{
    "claim": "...",
    "source": "repo/path.py:L10-L30",
    "confidence": "direct|inferred",
    "scope": "version 1.2.12",
}

这样审阅者能区分源码事实、文档承诺和 Agent 推断。

失败隔离#

子图可以拥有自己的重试和 fallback，但父图仍要定义：

  • 子图超时后是降级、跳过还是终止；
  • 部分并行结果是否足够；
  • 子图暂停时，父 thread 如何呈现；
  • 子图版本升级后旧 checkpoint 是否兼容。

不要让每个子 Agent 无限内部重试，然后父图再整体重试。预算会成倍放大。

部分成功应成为明确的聚合状态#

并行研究中，一个专家超时，其他已返回。产品可以允许降级报告，也可以要求全部结果齐全；图不会替你选择。保存每个子任务身份、状态与来源，聚合节点按合同决定继续、重试或停止。

只重跑失败专家可减少重复费用，但汇总前仍检查其他结果是否过期。独立子图的价值在于可测试边界，不在于把所有失败藏在另一个 Agent 里。

源码入口#

  • langgraph/graph/state.py：编译子图节点。
  • langgraph/pregel/main.py：subgraph 与 stream 处理。
  • langchain/agents/factory.py：可命名的 compiled agent graph。
  • 官方 Subgraphs 与 Multi-agent 文档。
