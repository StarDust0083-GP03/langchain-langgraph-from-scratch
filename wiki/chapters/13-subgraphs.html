子图与多 Agent：先隔离上下文

源码快照 2026-09-22 · 约 12 分钟

观测研究可能同时涉及仪器规则和历史资料。把它们拆成两个专家之前，应先决定每个专家允许看到什么、返回什么，以及失败怎样影响申请。增加角色名称不会自动产生知识或可靠性，清楚的数据边界才使拆分有价值。

子图提供一个可独立定义状态和完成条件的单元。它可以包含模型，也可以完全由确定性节点组成；多 Agent 只是使用子图的一类方式。

先问为什么要拆#

若历史资料检索需要独立权限、上下文很长，且结果能用窄对象返回，就值得考虑子图。它可以单独测试和升级，也能把主流程不需要的工具尝试留在内部。

如果只是同一份两条规则分别加上“仪器专家”和“研究专家”的 prompt，收益可能很小，却多出模型调用、路由和预算管理。先用一个 Agent 配合确定性预算工具，遇到可复现的上下文或权限问题再拆，比较拆分前后的轨迹质量与成本。

子图的两种数据边界#

共享 state key#

父子图拥有同名且含义相同的字段时，可把编译子图直接作为节点。比如二者都使用 question 和 findings，子图读问题、回传核验结果，父图继续审批。

共享意味着更紧的合同：reducer、字段版本和可见范围必须一致。两个子图都写 messages 时，要确认它们是否真的属于同一消息历史，而不是为了少写映射把不同专家对话混到一起。持久化还需理解父子 namespace 和 checkpointer 配置。

显式输入输出转换#

不同状态或权限范围时，父节点选择输入，调用子图，再映射允许结果。以下为已构造 instrument_graph 的包装片段：

def inspect_instrument(state):
    child_input = {
        "filter_name": state["filter_name"],
        "allowed_rules": state["allowed_rule_ids"],
    }
    checked = instrument_graph.invoke(child_input)
    return {"instrument_finding": checked["public_finding"]}

子图无法因为父状态含申请人私人信息就自动读到它，输出也只通过明确字段进入父图。真实接入还要正确传播配置和运行上下文，特别是涉及暂停和恢复时，不能把独立 invoke 当成无条件共享父保存地址。

专家不需要看到主流程的全部历史#

仪器子图需要滤镜名称和允许查询的规则，不需要审批人账号、通知地址或真实提交工具。窄输入降低误用和泄露范围，也让固定测试更容易构造。

输出则应包含直接观察、来源版本和未决项，不要返回完整工具日志让父模型再猜重点。若父图需要审计中间过程，可以在受控观测系统中保留子轨迹，不必把它们全部变成主上下文。

常见多 Agent 模式#

路由（Router）#

路由选择仪器、归档或澄清路径，适合问题类型较互斥的入口。输出可约束为枚举，并保留 unknown，避免把不支持的天体动力学问题硬塞进仪器专家。

路由错了时，应允许返回不适用结果再升级，而不是无限转发。测路由要覆盖混合问题与陌生领域，不只测试关键词明显的例子。

子 Agent（Subagents）#

主助手把“核对 SIM-FILTER-2@r1 的限制”交给窄子任务，完成后收集结果。主流程保留控制权，子任务不直接批准申请。

委托应有完成 schema、预算与允许工具。主助手只看到最终摘要不等于失败不存在，返回值需要明确成功、缺证据或依赖故障。

交接（Handoff）#

当研究结束进入值班审核时，可以正式转移当前处理角色和允许动作。应用需保存接收方、必要上下文与转移原因，确保下一轮交互由正确处理者接管。

一句“请找值班员”只是文本建议，不构成控制转移。真正 handoff 会改变路由和状态，并定义无人接手、超时或拒绝接手时如何处理。

自定义流程（Custom workflow）#

固定预算、两个研究子图、人工审批和本地发布可以混合在同一图中。模型只在需要解释或研究时参与，确定性规则直接由代码执行。

这种组合让关键约束更容易测试：任一必需核验缺失就不进入批准路径，拒绝只修订当前版本，预算耗尽有单独终态，不需要所有动作都由专家聊天决定。

上下文工程比角色描述重要#

角色提示可以说明研究侧重点，但质量更依赖实际输入：允许来源是否完整，单位是否明确，已确认事实是否与用户猜测分开，缺资料时能否返回未知。工具集合与完成 schema 同样影响专家能做什么。

对比两种上下文可看出差异。只写“你是精密仪器专家”仍可能让模型猜读出时间；直接给出 SIM-TIME-4@r1 的 20 秒与 300 秒，并要求只使用已引用开销，才有可核验的计算依据。

多个角色的多数意见不是独立证据#

三个专家都引用同一条错误规则，只产生一个共同错误来源，不是三份独立支持。聚合应按资料身份与版本检查依赖，记录分歧来自规则、计算还是推断。

比如两个专家说余量 300 秒，一个说 400 秒，应重算 6 × 200 + 300，而不是投票。确定性计算可以直接裁决算术，资料是否适用则要回到原规则与使用范围。

记忆放在哪一层#

子图内部临时查询和工具观察留在其 state，父流程所需结论映射回父 state，跨调用继续靠 checkpointer，跨申请共享的已确认偏好用 store。每份数据只在需要的范围复制。

若子图应每次独立研究，不要无意复用持久子会话；若需要多次交互积累，则明确其保存配置与身份。父 thread、子 namespace 和业务申请号是不同标识，应分别命名和测试。

并行专家与聚合#

规则和归档查询互不依赖时可以并行。聚合结果应包含每项任务的身份和状态，让父图判断哪些已完成、哪些仍缺失。一个教学证据对象可写为：

finding = {
    "task_id": "filter-check",
    "claim": "Halpha 方案仍需真实仪器配置核验",
    "source": "SIM-FILTER-2",
    "revision": "r1",
    "basis": "fixture_observation",
    "status": "complete",
}

basis 区分教学记录、源码事实或模型推断，不把一个置信分数当成来源。真实系统应使用自己的枚举与 schema 校验，并在聚合时按任务 ID 排序去重，而非简单拼接长篇专家发言。

失败隔离#

父图应定义子图超时、暂停和失败分别如何呈现。部分成功是否可继续，取决于结论需要哪些证据；仪器安全核验缺失时，不能为了出报告跳过。

重试额度也要分层。两个子任务各最多尝试两次，父图再整体重跑三次，最坏可能出现十二次依赖调用。明确总预算，并优先重试失败的窄任务，避免成功结果和费用被重复放大。

部分成功应成为明确的聚合状态#

可保存 filter-check=complete、archive-check=timeout，然后给出“规则已核验，归档证据尚缺”的结果。它不同于整体失败，也不同于全部通过。

等待重试期间，已完成结果可能过期。聚合前检查来源版本和时效；若失效，则说明为何重新核验。隔离失败不等于隐藏失败，父层必须收到足够信息来作决定。

源码入口#

  • langgraph/graph/state.py：查看编译子图作为节点的连接方式。
  • langgraph/pregel/main.py：核对子图状态、保存和流式处理。
  • langchain/agents/factory.py：检查可嵌入的编译 Agent 图。
  • 官方 Subgraphs 与 Multi-agent 页面：对照共享状态、显式映射及协作模式的公开合同。

可先构造一个不含模型的仪器子图，验证输入隔离和结果映射，再决定是否需要独立专家循环。
