第 06 章

create_agent 到底创建了什么

源码快照 2026-09-22 · 约 16 分钟

观测规则问答通常符合一个循环：模型缺资料时请求工具，看到结果后继续研究，材料够了就回答。create_agent() 把这种常用形状和组件协议组装成图，返回 CompiledStateGraph。工厂调用本身不会完成研究，也不会因为返回值叫 Agent 就自动保存所有运行数据。

先区分构建和执行，才能判断工具未出现、审批未暂停或结构化结果缺失，应从哪一层排查。

默认图形#

把本章默认循环画成请求与观察的往返表，而不只看节点名称：

当前执行位置 本次产物 下一次被调度的工作
入口 输入消息进入状态 model 读取当前上下文
model search_notes 与预算调用 tools 处理这一轮请求
tools 两项带调用 ID 的观察 model 重新读取新增证据
model 不含普通待执行调用的回答 正常结束，或由已配置策略继续处理

这是省略中间件与结构化输出分支的教学形状。真实图会依据配置增加 hooks 和策略节点，无工具时也无需普通 tools 循环。判断当前图形应看工厂输入和编译结果，而不是假定每个 Agent 都有完全相同的边。

工厂阶段做了什么#

工厂将模型、工具、输出 schema 和中间件声明整理成可编译图。字符串模型标识需要初始化，字符串系统提示转换为消息，普通函数转为工具；供应商内置工具与应用执行工具的处理路径并不完全相同。

接着收集中间件的工具、状态字段和 hooks，组合模型与工具调用 wrapper，建立模型节点、工具节点及路由。最后把 checkpointer、store 和中断配置传入编译。这个过程决定能力集合和控制结构，不决定每次生成的具体参数。

定位问题时可列一份构建清单：注册了哪些工具，输出策略是什么，哪些中间件增加了节点，是否真的绑定 saver。只设置 thread_id 而未提供保存实现，无法得到期望的会话恢复。

工厂构建发生一次，模型选择发生多次#

同一个编译图可用于多个独立 thread。模型每次运行时读取当前消息，可能查询 SIM-TIME-4，也可能直接解释已有结果。产生新的调用只在既定能力范围内选择，不会把未注册的提交函数变成工具。

因此，工具名不存在应查构建输入，工具可见但从未选择应查描述与上下文，参数合法却被拒绝应查领域授权。把这些情况统一处理成更强烈的系统提示，会掩盖真正失败位置。

middleware 的四种作用#

改模型请求#

中间件可以在调用前选择本轮消息、系统提示、模型或工具列表。比如资料研究阶段只展示检索与估算，提交阶段才可能展示写操作。

这种变化应基于服务端可信阶段，不接受用户文字直接改权限。裁剪消息时还需保持近期工具交互闭合，不能删去请求却保留结果。

包模型调用#

wrapper 可记录请求、设置限额、尝试 fallback 或缓存结果。它围绕一次模型调用组织行为，不必成为独立的业务节点。

失败后换模型要重新核对工具与输出能力，不能只替换模型名。缓存键也需要覆盖影响结果的资料版本和策略，不能把旧规则下的建议返回给新申请。

包工具调用#

统一工具 wrapper 适合错误分类、尝试次数、审计与审批门控。它可以阻止未满足前置条件的请求，也可以将允许修正的参数错误转换为观察。

领域服务仍应再次授权。wrapper 配置错了不该导致跨课题组读数据，缓存命中也不能跳过当前对象权限检查。

在循环前后执行#

before/after model 或 agent hooks 可维护统计、摘要或业务字段，其中部分会形成图节点。这会改变状态更新与恢复的边界，不能把它们都当成无状态装饰。

如果一个 hook 写 store 或通知外部服务，应审查其重放行为。名字叫 after 并不表示它有不可重复执行保证。

wrapper 的顺序会改变你观察到什么#

设有缓存、授权检查与调用计数。缓存放在最外层且直接返回时，内层可能根本不执行；若授权也在里面，权限撤销后仍可能看到旧结果。安全检查应覆盖缓存命中路径。

再比较重试与计数：计数在外、重试在内，记录一次逻辑调用；计数在内则可能记录每次真实尝试。两种指标都有用，但必须命名清楚。用“缓存命中”“第一次超时第二次成功”“授权拒绝”三个输入分别检查 wrapper 顺序，比只看正常调用更有效。

context、state 与 store#

位置 本场景内容 如何变化
State 消息、当前草稿、资料引用、修订号 节点增量经 reducer 合并，可进入 checkpoint
Runtime context 可信课题组身份、连接依赖、运行设置 每次调用注入，通常按只读依赖使用
Store 跨申请的已确认仪器偏好或规则索引 由应用显式读写，独立管理生命周期

context_schema 描述运行时依赖形状。快照中的 config_schema 已有弃用提示，新实现应围绕 context 组织注入。配置中的 thread_id 则继续用于定位恢复实例，它不能替代授权主体。

如果批准状态只在 context 中，下一次请求可能缺失；如果数据库连接放进 state，序列化和恢复会失败或保存无意义对象。按用途选择容器，能避免把持久化当成任意 Python 对象快照。

结构化输出的选择#

response_format=Schema 允许工厂依据模型能力选择原生 ProviderStrategy 或工具形式的 ToolStrategy；显式策略则需要调用方承担兼容性判断。不同策略可能改变内部请求与路由，不能把所有工具形状都当成外部副作用。

结果在 state 的 structured_response 中读取。比如结论对象可以含 total_s=1500、资料编号和未核验事项。字段校验只能约束类型和声明规则，真实证据仍需核对，不能从 schema 通过直接推出申请获批。

高级工厂并没有消除图#

以下为应用已提供模型、工具和存储后的构建片段：

from langchain.agents import create_agent

agent = create_agent(
    model=chat_model,
    tools=research_tools,
    system_prompt="只根据允许的观测资料提出建议，列出尚未核验的条件。",
    checkpointer=saver,
    store=knowledge_store,
)

运行时仍使用图的 thread、stream 和 checkpoint 语义。动态 interrupt() 暂停后通过 Command(resume=...) 提供决定；如果用 interrupt_before 设置静态断点，继续执行通常传 None，不能把两种暂停混为一谈。

工厂图也可以被父图作为研究节点使用。外层负责固定预算与审批，内部 Agent 自主补资料，便能在不重写工具循环的前提下加上业务阶段。

create_deep_agent：预装好的 harness#

当研究需要工作文件、长任务清单、技能加载和窄任务委托时，create_deep_agent 提供一组现成组合。它继续建立在 LangGraph 上，默认能力与签名则取决于单独安装的 deepagents 版本。

在天文台场景中，是否需要文件工具取决于资料处理方式。只查两条规则时，整套 harness 可能多余；需要生成多份研究附件时，才值得检查 backend、摘要和子 Agent 的组合。第 16 章会逐项讨论，不把默认工具等同于默认安全。

何时离开 create_agent#

如果要求预算计算完成后必须独立核验，再由值班员批准，且任一失败有固定结束状态，显式 StateGraph 更容易检查依赖。模型无需成为每一个阶段的路由中心。

如果变化只是更换 prompt、限次重试或增加一种最终 schema，先使用工厂配置和中间件。自定义图接管的是控制结构和恢复责任，不应仅为获得更多节点名称而增加。

结构化结果应该从正确字段读取#

自然语言说“可以安排”，不等于 structured_response 中所有条件满足，更不等于人工批准。调用方应读取约定字段，再执行独立的数值、引用和权限判断。

当资料缺少滤镜配置时，输出合同应允许缺失和未知，而不是强制一个批准布尔值。否则模型容易为了满足格式给出错误确定性。区分研究结论、审批结果和真实提交回执，可以防止三个不同状态挤进一个 approved 字段。

源码入口#

  • langchain/agents/factory.py：从返回类型、节点创建和条件路由追组装。
  • langchain/agents/middleware/types.py：检查 hooks 与 wrapper 合同。
  • langchain/agents/structured_output.py：核对 schema 策略和结果位置。
  • langgraph/prebuilt/tool_node.py：追普通工具请求的执行与回填。

阅读时先选无工具、普通工具、结构化输出三个小配置比较，再加入中间件，避免一次面对全部工厂分支。
