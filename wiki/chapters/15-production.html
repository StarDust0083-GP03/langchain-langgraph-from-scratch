生产检查表与源码阅读路线

源码快照 2026-09-22 · 约 16 分钟

离线申请能走到本地回执，只说明特定输入下控制流成立。真实系统还要面对排班变化、请求重复、进程退出和旧任务恢复。上线判断应有失败输入与可重复验证，不能由一次顺利演示代替。

本章把这些验证绑定到观测申请对象，再给出追踪源码的方法。逐项填写失败输入、预期结果和已有测试，空白处就是还缺的证据。

上线前检查表#

状态#

为 total_s 固定单位和公式版本，为 notes 固定来源身份与去重规则，为 draft 和 revision 固定覆盖关系。并行节点的写入集合应可列出，冲突字段有明确聚合节点或 reducer。

检查最大规模和出口：整幅观测图像不应反复进入 checkpoint；模型输入窗口与恢复状态分别管理；用户事件只输出白名单字段。测试中放入敏感哨兵值，确认它没有出现在不允许的出口。

控制流#

明确无资料、超预算、拒绝耗尽和正常完成四类状态，不能只检查图是否结束。循环记录剩余额度或版本，取消和超时也有可解释结果。

并行核验需要哪些结果、是否允许降级，应在聚合规则中写明。空输入集合、某支路超时和延迟决定都要测试，避免正常路径图像掩盖缺失依赖。

工具与副作用#

每个入口校验单位、范围和身份，敏感写操作核验当前批准版本。模型可见工具列表只是前置限制，领域服务仍做最终授权。

真实窗口预留和通知使用稳定业务键，记录参数指纹与外部回执。超时先查结果，不把未知状态改成未执行。对同一键不同参数的请求，服务应明确拒绝冲突，不能静默返回无关旧结果。

持久化#

用可信申请映射 thread，防止跨组恢复。检查 saver 初始化、迁移、备份和保留策略，store namespace 由服务端身份构造。

跨进程恢复要实际执行，旧 checkpoint 要在新图中验证语义。同一实例并发调用如何串行化或拒绝也需定义，不能依赖 UI 按钮只点一次。

观测与评估#

运行记录关联申请、run、图版本、资料版本和必要模型配置。指标分开统计研究耗时、外部等待、尝试次数与人工等待，避免把一天审批误判成模型延迟。

答案评估检查引用、算术和未知项，轨迹评估检查权限、调用次数及预算。失败样本脱敏后进入回归，trace 本身也应控制访问和保留范围。

把检查表还原成一次真实故障#

假设远程排班已预留窗口，应用保存回执前崩溃。恢复从旧状态重试提交，若业务键不稳定，就会重复占用；若 thread 归属未校验，另一个课题组还可能触发这次恢复。持久化、幂等和授权必须沿同一条链检查。

再看答案正确但轨迹错误的情况：最终 1500 秒计算无误，却读了未授权资料并发出十次重复查询。仅按答案评分会放过问题，轨迹需要记录资料身份、工具次数和拒绝信息，而不是为了排障直接保存全部私密内容。

四类测试#

1. 确定性节点测试#

用固定参数直接检查预算、资料映射和修订更新。6 帧得到 1500 秒，8 帧得到 1900 秒；负帧数、错误单位或未批准发布应被拒绝。失败时能直接定位函数，而不必解析整条 Agent 对话。

2. 图结构与路由测试#

用固定节点或 fake model 驱动整图，断言待恢复节点、资料数量、版本变化和终态。刻意覆盖拒绝不发布、第三版停止、并行字段冲突等负面路径。

当前 examples/test_examples.py 提供这一层的部分回归。它使用内存保存，不测试跨进程，也不证明所有并行模式；后续增加新控制路径时，应增加对应最小断言。

3. Provider 合同测试#

针对计划使用的 provider，少量验证工具 schema、消息闭环、结构化结果和 chunk 合并。用受限请求和费用预算运行，记录目标模型及适配包版本。

本地 fake 无法证明真实服务接受某种消息排列；真实服务一次成功也不能覆盖所有图分支。两层测试各有用途，不应互相替代。

4. 轨迹评估#

检查实际查询是否都在白名单来源内、预算工具是否使用正确参数、是否无故重复调用、最终草稿是否遗漏未核验事项。对相同答案，合理轨迹与危险轨迹应得出不同评估结果。

可建立失败样例：不可信资料要求绕过审批、超预算方案被模型美化、过期版本请求继续发布。评估关注能观察到的行动，而不只是措辞是否谨慎。

升级策略#

升级前记录依赖、图 schema 与资料合同版本，读目标变更，再运行确定性回归和少量 provider 合同测试。新 thread 能正常生成后，还要恢复旧暂停实例，比较批准、拒绝和取消分支。

采用分批发布时，观察错误率、图步数、工具尝试数、费用和恢复失败，不只比较总延迟。若涉及 channel 或 checkpoint 格式，回滚方案要包含旧实例如何继续，不能仅退回代码包。

DeltaChannel 等 beta 能力有额外格式约束。旧运行时不能理解新存储时，应隔离受影响 thread、迁移或让兼容版本跑完，而不是强行加载后假定结果正确。

升级测试为什么必须带一份旧 checkpoint#

旧状态可能保存 review 节点和秒为单位的窗口，新版若改节点名或把窗口解释成分钟，反序列化成功也会误判。用脱敏旧副本恢复，核对待审 revision、1500 秒预算与后续回执身份。

测试副本不能连接真实提交服务，避免把升级验证变成第二次预留。需要外部合同测试时，用隔离环境和独立业务身份，并明确哪些结果来自模拟、哪些来自真实服务。

源码阅读路线#

想看 Agent 工厂#

先在 langchain/agents/factory.py 找返回类型、模型节点、工具节点和条件路由；再查看 middleware/types.py 中 hook 合同、structured_output.py 的策略，最后进入 langgraph/prebuilt/tool_node.py 和 graph/state.py。

带着“哪项配置增加了哪个节点”比较几个最小构建，比先读完所有重载和兼容分支更有效。工具未注册与模型未选择要在这里分开诊断。

想看状态合并#

从 graph/state.py 中字段注解到 channel 的转换开始，查看 channels/last_value.py、channels/binop.py，再到 pregel/_algo.py 的 apply_writes。

记录旧值、两份节点更新和最终值，特别检查节点是否误返回整段旧列表。用一个来源 ID 的重复输入即可构造最小反例，不需要启动真实模型。

想看恢复与中断#

在 types.py 找 interrupt，通过 _internal/_scratchpad.py 查看恢复信息，再追 pregel/_loop.py、pregel/_checkpoint.py 及 saver 接口。

同时列出中断前的所有副作用和非确定性读取。运行时能解释节点如何重入，领域服务才能解释再次调用为何不会重复预留，两条路径要一起看。

想看流式#

先核对 pregel/main.py 的公开方法与 mode，再进入 stream/run_stream.py、stream/_types.py 和相关转换器。不同版本的事件对象要按对应签名解读。

从一个 chunk 或 update 一路追到公网适配器，记录它何时被筛选、序号怎样分配。模型已产出而页面不动时，这条路径能定位缓冲发生在哪一段。

避免低效阅读#

不要按目录顺序把兼容代码都读一遍。先确定目标版本和失败对象，用符号检索找到生产者与消费者，再看测试是否已有相同边界输入。

公开 docstring 描述用法承诺，实现体现当前分支，测试帮助理解限制；三者不同就先核对版本和调用路径。带 deprecated 标记的历史入口不应自动成为新代码设计依据，平台宣传也不能替代恢复与事务语义。

一次排查应该跟着对象走#

预算错了，追参数、公式与单位；资料重复，追节点返回值和 reducer；恢复批准错位，追 thread、revision 和恢复值；用户数据泄露，追 state 到事件适配器。

修复后保留最小失败输入与预期终态。比如 approved="false" 不应通过，v1 决定不应批准 v2。这样的回归比一句“加强校验”更能防止升级时重复同类错误。

最终心智模型#

要定位的对象 主要层级 首个检查点
模型请求与工具观察 LangChain 协议与 harness 名称、schema、调用 ID
草稿版本与后续节点 LangGraph 状态转换 partial update、路由、批准合同
同步步骤与并发合并 Pregel 触发、channel、写入与保存
真实窗口与通知 应用领域服务 授权、幂等键、外部回执
页面和诊断轨迹 事件适配与观测系统 出口白名单、消费及重连合同

按对象定位后，再选择工具或源码入口。框架能帮助组织执行，申请所依据的事实、权限和外部状态仍需有各自可验证的记录。
