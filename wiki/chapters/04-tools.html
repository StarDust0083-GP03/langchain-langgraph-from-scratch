工具调用：Schema、执行与结果回填

源码快照 2026-09-22 · 约 10 分钟

工具是模型世界与真实系统之间的窄门。设计得好，模型只需要做选择和填参数；设计得差，模型会猜测内部 ID、绕过权限边界，或把一次操作拆成无法恢复的半成品。

从函数到工具#

最短写法是装饰普通函数：

from langchain.tools import tool

@tool
def search_notes(query: str, limit: int = 5) -> str:
    """Search approved local notes for a technical question."""
    ...

框架从函数名、类型标注和 docstring 构造名称、描述与输入 schema。三个字段分别回答：

  1. 这个能力叫什么？
  2. 什么情况下应该用？
  3. 输入必须满足什么结构？

类型标注不是文档装饰。它会进入 schema，也会影响运行时校验。复杂参数适合用 Pydantic 模型明确约束，但不要为了“结构化”把简单工具拆成十几个字段。

参数合法，与操作允许是两道门#

schema 能说明 limit 必须是整数、query 必须是字符串，却不能证明调用者有权搜索某个租户的资料。用户身份应由服务注入，不能让模型在公开参数中任选。否则模型生成完全合法的 JSON，也可能代表错误主体读取数据。

工具描述还要说清适用条件。名称叫 search 很泛，说明只检索审核本地笔记、返回引用，会让模型更容易选择正确入口。描述不是执行保障，工具内部仍要限定路径、结果大小和权限。

BaseTool 也是 Runnable#

源码中 BaseTool 继承 RunnableSerializable，因此工具拥有 invoke、ainvoke、batch 和配置传播能力。这解释了为什么 callback、tag、metadata 和 runtime config 能沿 Agent 调用传下去。

工具执行的关键边界仍然是：

模型输出 tool_call
  -> 查找注册工具
  -> 校验参数
  -> 注入 runtime/state/store
  -> 执行同步或异步函数
  -> 格式化 ToolMessage

模型不会直接调用 Python 函数。执行器决定是否允许调用，以及如何处理异常。

ToolNode 解决什么#

LangGraph 的 ToolNode 负责标准工具节点的繁琐部分：

  • 从最后一条 AI 消息提取工具请求；
  • 根据名称匹配工具；
  • 对多个调用并行执行；
  • 把返回值转换为 ToolMessage；
  • 注入状态、store 和 runtime；
  • 按配置处理工具错误。

这不是简单的 for call in calls。一旦加入并行、异步、注入和命令式状态更新，手写执行器很容易漏掉协议细节。

并行工具执行没有自动形成一个事务#

模型同一轮请求“创建工单”和“发送通知”，ToolNode 可以分别执行，但第一项成功、第二项失败时，不能声称整组要么都成功要么都失败。每个工具应返回可识别的业务状态，后续计划根据实际结果补偿，而非把整组盲目重试。

只读检索通常比较容易重试；外部写操作需要稳定幂等键。tool_call_id 可以追踪一轮请求，但模型重新规划后可能生成新 ID，因此关键副作用最好使用订单或流程实例等业务身份去重。

返回文本、对象还是 Command#

多数工具返回字符串或可序列化对象，随后被包装成工具消息。需要同时更新图状态时，可以返回 Command(update=...)。例如查询客户资料后，既告诉模型摘要，又把客户 ID 写入状态。

应谨慎使用 Command。工具如果随意改多个状态字段，会让数据流隐藏在执行器内部。只有“工具结果本身就是状态变化”时才值得这样做。

结构化输出不是普通工具#

让模型最终返回一个 Pydantic 对象，常见实现有两条：

  • Provider strategy：使用供应商原生结构化输出能力。
  • Tool strategy：把目标 schema 表示成一个特殊工具调用。

create_agent(response_format=Schema) 会依据模型能力选择策略。结构化结果应接受校验失败和重试，而不是假设模型生成的 JSON 一定合法。

工具调用用于请求应用执行动作，结构化输出用于约束最终答案。两者底层可能都使用 schema，但业务含义不同。

工具权限放在哪里#

静态白名单#

创建 Agent 时只注册当前场景允许的工具。没有注册的能力就不能执行，这是最可靠的第一层。

动态选择#

中间件可根据用户角色、会话阶段或功能开关筛选工具。动态策略必须以服务端身份为依据，不能相信用户消息里自称管理员。

工具内部校验#

最终权限检查仍在工具内部或它调用的领域服务中。即便路由层出错，敏感操作也不应越权。

注册集合限制能力面
    + 中间件限制当前可见集合
    + 领域服务执行最终授权

副作用与幂等#

发送邮件、扣库存、创建工单都应接收幂等键。Agent 的节点可能因重试或中断恢复而再次执行，不能把“框架通常只调用一次”当作事务保证。

推荐记录：

  • tool call ID 或业务幂等键；
  • 参数摘要；
  • 调用者与审批结果；
  • 执行状态和外部系统返回 ID。

超时也不代表外部操作失败。先按幂等键查询，再决定是否重试。

超时后怎样确认一封邮件究竟发没发#

发送请求超时，可能是邮件服务没有接到，也可能是发送成功但响应丢了。直接重试会产生两封。工具可以先按业务幂等键查询外部状态，已成功则返回原结果，未完成再按服务契约重试。checkpoint 保存的是图状态，无法填补外部系统与图存储之间的事务空隙。

审批也不应只保存在 prompt。执行工具时核验当前对象、批准版本与调用者；审批期间草稿已被替换，就不能沿用旧预览的同意。schema、路由、审批和领域授权分别回答不同问题。

常见误区#

  • 把秘密放进工具描述：schema 会发给模型或观测系统。
  • 返回无限大的结果：应摘要给模型，把原文放到外部存储或 artifact。
  • 一个万能 SQL 工具：权限面过大，参数空间也太自由。
  • 用 prompt 做授权：提示只能引导，不能阻止执行。
  • 吞掉所有异常：模型收到“成功”会继续基于错误状态行动。
