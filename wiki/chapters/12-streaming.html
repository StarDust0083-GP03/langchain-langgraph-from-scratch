流式输出不是一种流

源码快照 2026-09-22 · 约 10 分钟

“打开 streaming”并不能说明客户端会收到什么。LangChain 与 LangGraph 可以流模型 token、节点更新、完整状态、调试事件和自定义进度。选择错误的模式，轻则页面不更新，重则把内部状态和敏感字段直接发给用户。

四类常见需求#

模型消息流#

用户想立即看到回答文字。消费端关注模型消息 chunk，逐步拼接 content 和工具调用片段。

状态更新流#

调试或业务 UI 想知道哪个节点刚完成以及写了哪些字段。updates 关注每步增量，不传输整份累计状态。

状态快照流#

需要观察每一步后的全量 state 时使用 values。它最直观，但数据量大，而且可能包含内部 channel。

自定义进度流#

长工具可主动发出“已扫描 120/500 个文件”一类事件。它不应伪装成模型文本，也不必写进持久 state。

同一轮运行，可以有两种不同的时间线#

模型文字流告诉用户答案正在形成，节点更新流告诉应用哪一步已经完成。search 返回 notes 时，页面可以显示“找到三份资料”；draft 流出文字时，页面逐步展示草稿。若只监听模型 token，没有文本输出的检索阶段看起来会完全停住。

反过来，values 快照适合受控调试，不适合直接作为公网响应。里面可能含内部计划和 artifact。外部协议应选择需要的事件字段，让“进度”“文字”“等待审批”和“错误”有不同类型。

stream mode 是数据合同#

典型调用：

for chunk in graph.stream(inputs, stream_mode="updates"):
    handle(chunk)

异步服务应使用异步消费，避免阻塞事件循环。当前源码还提供更丰富的 event streaming 版本和 transformer 管线，但公开给客户端前应转换成自己的稳定事件协议。

推荐的外部事件形状：

{
  "type": "message.delta",
  "run_id": "...",
  "sequence": 17,
  "data": {"text": "Lang"}
}

事件应有类型、顺序号和 run 标识。客户端重连时才知道是否重复、丢失或属于另一轮执行。

工具调用参数不能边到边执行#

模型可能这样流出参数：

'{"query"'
': "Lang'
'Graph"}'

前两个片段都不是完整 JSON。框架会合并消息 chunk，应用若直接转发 provider 原始 delta，则必须等工具调用完成事件后再执行。

UI 可以提前展示“模型准备调用 search”，但不能把未完成参数当作授权后的动作。

背压与取消#

生产流不是无限 yield。需要考虑：

  • 客户端读得比模型产生慢时，缓冲区上限是多少；
  • 用户关闭页面后，图是否继续；
  • 断线后结果保留在哪里；
  • 同一 thread 是否允许两个并发 run；
  • tool 仍执行时，取消是软取消还是强终止。

对有副作用的工作流，客户端断线不应等价于事务回滚。可让 run 在后台继续，并通过持久状态重新订阅。

消费慢与停止运行是两个问题#

客户端读取变慢，服务可能积累事件；如果缓存无限增长，一次长生成会消耗大量内存。可对展示进度合并、限制队列，并定义断开处理。文字增量不能随意丢片段，否则用户得到残缺答案。

客户端关闭页面不保证模型 provider 和工具操作已经取消。取消信号要沿任务传播，已发生的外部写入不能撤回。需要明确哪些阶段可停止，哪些必须先确认业务结果，再把最终状态保存供重连查询。

私有状态也可能被流出#

Input/Output schema 约束 invoke 的接口，不自动过滤所有 stream mode。官方 Graph API 文档指出，values 默认可包含内部或私有 channel。将原始 state stream 直接桥接到浏览器之前，必须做字段白名单。

同样，trace 和 debug events 可能包含 system prompt、工具参数、检索原文和错误栈。开发方便不代表适合终端用户。

observability 与用户流分开#

用户流优化稳定、简洁和可恢复；观测流优化细节和诊断。两者可以来自同一次 run，但不应共用一个未经筛选的 payload。

                       ┌─ 用户事件适配器 -> SSE/WebSocket
Graph event stream ────┤
                       └─ 观测适配器 -> trace / metrics / logs

这样升级框架事件格式时，只修改适配器，前端合同不必跟着内部 API 变化。

测试流式行为#

不要只断言最终文本。还要检查：

  • sequence 单调增加；
  • chunk 合并后等于最终消息；
  • tool call 完成前没有执行；
  • interrupt 事件能结束本轮消费；
  • 私有字段没有出现在用户通道；
  • 慢消费者和断线不会无限占内存。

重连时如何避免把同一段文字显示两次#

外部事件带 run_id 和递增序号，客户端可以识别重复；服务端还需定义重放窗口或查询最终状态的入口。展示已完成草稿和继续 token 流不是同一种恢复，不能让 UI 把全量快照再次追加成增量。

测试应故意在工具执行、模型输出和审批等待时分别断开，再确认没有泄漏私有字段、重复执行副作用或串到其他 run。用户流强调稳定合同，调试 trace 可以更丰富，但两者访问权限不同。
