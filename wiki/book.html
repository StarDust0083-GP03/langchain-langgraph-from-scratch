读前说明：这本书怎么读

一份观测申请已经生成草稿，值班员还没有批准，服务却重启了。重新打开页面时，系统应找回草稿、认出待审版本，继续等待决定。它不能重新占用望远镜时段，也不能把另一份申请的批复套过来。理解 LangChain 与 LangGraph，可以从这件具体的事开始。

书中的主线是天文台观测申请与资料研究助手。我们会把申请拆成消息、工具观察、状态更新和可恢复任务，再观察这些对象经过框架的哪些接口。读者需要基本 Python 知识，不需要天文专业背景；所有观测参数都用于教学，不构成真实仪器操作建议。

本书回答什么#

读完后，你应能解释一段运行轨迹，知道每项输出由谁产生、依据什么。比如模型请求估算时长时，谁校验帧数，谁计算预算，结果靠什么身份回到模型；审批暂停后，哪些数据已经保存，恢复时哪些函数会再执行；两个检索节点同时补材料，为什么不能争写一个普通列表字段。

我们也会区分几个容易混淆的责任：LangChain 提供组件协议与常见 Agent 组合，LangGraph 表达可恢复的状态转换，Deep Agents 预装通用工作能力，LangSmith 提供观测等平台能力。框架能保存执行位置，申请是否有足够证据、用户是否有权提交，仍需业务代码判断。

源码阅读集中在这些问题上。你会看到消息合并、工具执行、图编译、步骤调度以及持久化的入口，不会在每个供应商的参数之间来回切换。模型选择影响生成质量，但不能替代授权、预算和恢复设计。

跟着一份状态读，而不只记住名字#

设申请编号为 SIM-OBS-17，研究 Halpha 窄带成像，拟拍 6 帧，每帧曝光 180 秒。教学规则规定每帧读出 20 秒，整份申请另有 300 秒校准时间。因此总预算是 6 × (180 + 20) + 300 = 1500 秒，在 1800 秒的模拟窗口内剩余 300 秒。

这几个值会贯穿不同章节，但每章检查的对象不同。消息章节关心估算请求和结果的配对；状态章节关心 total_s 何时从不可用变为 1500；中断章节关心批准的是 v1 还是修订后的 v2；生产章节则检查时长、资料版本和权限是否在恢复后仍有效。计算满足预算，不代表目标可见或天气合适，系统要把这些未核验项留在草稿里。

可以边读边记录三个时点：节点输入快照、节点返回增量、合并后的下一快照。这样遇到重复材料或审批丢失，能指出是哪一次转换出了问题，而不是笼统归因于模型不稳定。

如何看源码引用#

章节末尾的路径是检索起点。先找到公开方法的输入和返回值，再找到构建或包装代码，最后追踪运行时消费这个返回值的位置。比如节点返回 Command 后，继续找路由与写入处理，才能知道更新和跳转如何共同生效。

当文档和实现看起来不一致，先核对版本及是否走到同一个分支。测试文件常能给出最小边界输入，尤其适合核对重复消息、并行写入和恢复顺序。可以用一次手算检查理解：写出节点输入、返回增量和合并结果，核对它们是否与运行轨迹一致。

01

四层栈，一条执行链

天文台助手既要读资料，又要等待人确认申请。前者涉及模型、消息和工具的协作，后者涉及流程状态的保存与推进。LangChain 与 LangGraph 分别把这两组责任组织起来，因此同一个应用常会同时使用它们。

在本书快照中，create_agent() 的产物是 CompiledStateGraph，langchain 的依赖也包含 langgraph。Deep Agents 在这个组合上增加预装能力；LangSmith 从运行旁路收集轨迹、支持评估等平台工作。四个名字不对应四个必须逐一经过的网络服务，最小离线程序可以完全不连接平台。

用一次研究任务看清每层负责什么#

用户要求判断一份 Halpha 申请是否装得进 30 分钟窗口。LangChain 消息保存原问题，模型接口返回两个工具请求，执行器将资料与计算结果分别关联到调用 ID。估算得到 1500 秒后，模型才有依据说明还有 300 秒余量。

LangGraph 可以要求先保存草稿，再到审批节点暂停；拒绝时只修订草稿，不重新检索已经确认的规则。Pregel 负责执行这些已激活节点，并让更新在后续步骤可见。即使完整轨迹都被 LangSmith 记录，也不能由此推出目标当晚可见，因为示例没有执行天体位置计算。观测只能记录做过什么。

LangChain 的四块底座#

消息#

一次申请中，用户要求、模型提议和工具观察具有不同来源。HumanMessage、AIMessage、ToolMessage 保留这种身份区别。工具结果通过 tool_call_id 指向请求，usage 和响应元数据则帮助解释模型调用的成本或来源。

如果把两次估算都改写成普通文本，应用便难以确认 1500 秒对应 6 帧还是另一个方案。消息对象让关系可被程序检查，但外部文档中的文字仍要作为不可信材料处理。

模型#

BaseChatModel 为单次、批量和流式调用提供共同表面，provider 适配层负责协议转换。业务可以用统一消息调用不同模型，但目标 provider 是否支持并行工具或原生结构化输出，要单独核验。

模型返回的内容只是一次推断。它选择 estimate_time，并不代表计算已经发生；它说申请合理，也不代表审批完成。把这两种状态区分开，才能替换模型而不改变领域规则。

工具#

工具把描述、输入 schema 与可执行函数关联起来。观测预算工具可公开 frames 和 exposure_s，服务端则注入可信申请人身份。模型负责提出参数，执行层检查范围、权限，再调用函数。

名称和描述影响选择质量，执行函数控制实际边界。如果只把身份写进 prompt，工具服务仍接受任意申请编号，就没有形成可靠授权。相同工具接口可以包住本地计算或远程请求，副作用风险取决于后者实际做什么。

Runnable#

Runnable 允许组件通过 invoke、ainvoke、stream、batch 等表面组合起来。比如规范化资料查询、检索、构造提示和解析响应，可组成一个可追踪单元。

接口一致不代表实现都原生流式或真正批处理。普通同步函数可能借线程运行异步入口，某个解析步骤也可能缓冲全部文本。性能和取消能力要追踪具体实现，不能由方法名字推断。

LangGraph 增加了什么#

申请流程包含多个时间尺度：检索用毫秒或秒，模型生成需要更久，人可能隔天才审批。普通函数调用栈很难横跨这些等待，图把可恢复位置表达为状态与待执行任务。

State 保存当前草稿和材料，Node 产生局部更新，Edge 决定后继，Reducer 规定并发增量怎样合并。Checkpointer 记录 thread 的执行状态，Store 保存可跨申请读取的数据，Interrupt 把决定交到图外。每个概念都回答一个运行问题，不需要为了用全它们而增加字段。

为什么组件协议不能替代运行时#

工具协议能告诉执行器 1500 秒是哪个调用的结果，却不会在进程重启后自动找回待审 v1。反过来，图可以恢复草稿，但若工具结果 ID 配错，恢复的也是一份错误上下文。

调试时可以用两个独立检查缩小范围：消息合同是否完整，状态转换是否在正确边界落盘。预算结果缺失先查工具回填，待审批申请变成新任务先查 thread 配置。组件协议和运行时在这两条路径上协作，不承担对方的全部责任。

三种使用层级#

业务入口可以按接管多少控制流来选择；Pregel 则是通常不必直接操作的底层。

起点 天文台场景中的适用需求 接管的责任
create_deep_agent 研究需要文件、任务清单和子任务 检查默认工具与 backend，删除多余能力
create_agent 模型自主查规则、反复补资料 定义工具、上下文、预算和错误策略
StateGraph 或 Functional API 固定计算、独立核验、人工批准有明确顺序 显式定义状态、依赖和恢复路径

选择更低层意味着承担更多组装工作，不保证更高质量。标准循环若已覆盖资料问答，增加自定义路由只会扩大测试面。需要精确控制批准后才能生成提交请求时，显式业务图则能让这条约束更容易验证。

什么时候不需要它们#

如果只是计算 6 × 200 + 300，一个 Python 函数足够。若用户只需在资料库里查关键词，先做好搜索与引用展示，不必强行让模型决定每一次查询。仅有一次文本改写时，provider SDK 也可能比完整 Agent 更合适。

引入框架的理由应来自实际边界：是否组合多类组件，是否存在条件循环，是否需要跨请求恢复。一个稳定的任务队列已经能解决确定性后台工作时，也可以保留它，让图只处理确实需要的那部分交互。

怎样决定是否下沉到自定义图#

把需求写成能失败的断言。比如“资料核验和时间预算都完成前，不得展示审批按钮”，这需要清楚的依赖与聚合；“回答语气更简洁”只改变模型请求，通常不用改图。

再比较两种实现的恢复路径。如果标准循环内隐藏了大量阶段标志，每次恢复都要猜当前处于哪一步，拆图可能有益。如果只是为了让图更好看而拆分三次字符串处理，独立 checkpoint 与节点名称反而会增加维护成本。

02

不用框架，先写出 Agent 循环

先把天文台助手缩到两个能力：查教学规则、估算拍摄时长。模型只决定请求什么，Python 执行器真正调用函数，再把观察交回模型。即便模型由固定脚本代替，请求、执行和回填三者也不能省略。

下面是控制结构的伪代码，不是某个 provider 的请求格式：

history = [user_question]
remaining = 4
while remaining > 0:
    remaining -= 1
    proposal = model(history, exposed_tools)
    history.append(proposal)
    if not proposal.calls:
        break
    observations = [dispatch(call) for call in proposal.calls]
    history.extend(observations)
else:
    raise RuntimeError("model turn budget exhausted")

一次模型响应里可以有多个调用，所以预算扣的是模型轮次，不是工具数。先把该轮所有观察补齐，再进入下一轮，能避免模型在缺了一半结果时做结论。

一次调用的完整轨迹#

固定输入为“研究 Halpha 观测申请：6 帧，每帧 180 秒”。示例的脚本模型产生资料查询和预算计算两个请求，执行器依次处理它们。

位置 消息身份 可检查的内容
0 user 用户问题与固定教学场景
1 assistant obs-rule 请求 search_notes，obs-time 请求 estimate_time
2 tool obs-rule 对应 SIM-FILTER-2 与 SIM-TIME-4
3 tool obs-time 对应总时长 1500 秒及计算式
4 assistant 用资料编号说明预算，同时声明未提交真实申请

执行器检查调用名称属于注册集合，并保留每个请求的 ID。工具消息即使调换到达顺序，也能靠 ID 还原关系；不过实际 provider 对消息排列的额外要求仍需适配层满足。

模型为什么还要再读一次工具结果#

第一次响应没有计算结果，只表达需要规则和预算。如果工具在 Python 中算出 1500，却只打印到终端而不回填消息，下一次模型调用依然没有这项观察。外部函数执行成功不会自动改变模型上下文。

完整结果还应包括适用范围。这里的 1500 只覆盖曝光、读出和校准，不涵盖真实排班。模型读到这条限制，才能把结论写成模拟预算建议。如果两项工具只返回其中一个，最终消息应该等待或报告缺失，不能用另一项代替。

工具 schema 是合同#

预算函数的 schema 可以把数值范围直接告诉模型。以下为示例中的工具定义形状，不是远程请求的完整外壳：

{
  "name": "estimate_time",
  "description": "估算教学申请时长，不查询真实排班",
  "parameters": {
    "type": "object",
    "properties": {
      "frames": {"type": "integer", "minimum": 1, "maximum": 30},
      "exposure_s": {"type": "integer", "minimum": 1, "maximum": 600}
    },
    "required": ["frames", "exposure_s"],
    "additionalProperties": false
  }
}

描述限定用途，schema 限定结构，执行函数再次校验范围。手写例子没有引入 JSON Schema 校验器，参数的最终保障来自 estimate_time() 中的显式判断。Python 的 bool 是 int 子类，因此函数用 type(value) is int 排除 True 被当作一帧，避免演示程序在边界输入上悄悄通过。

错误也是下一轮输入#

模型请求了不存在的工具时，执行器返回 unknown_tool；帧数为负数时返回 invalid_arguments。这些是可理解的观察，模型可以停止或调整方案。错误结果仍要带原调用 ID，不能因为执行失败就跳过回填。

依赖故障则不应全转成“参数不对”。示例只捕获 TypeError 和 ValueError，意外运行故障会传播出去，方便测试暴露真实问题。接入远程服务后，应另行定义有限重试、失败分类与脱敏信息，而不是用一个宽泛 except Exception 把所有故障写进聊天记录。

哪些错误应该让模型改计划#

资料查询返回 no_match，意味着当前允许搜索的语料没有命中。示例最后会说明证据不足，即使时长算得出来也停止建议。它没有偷偷退回一份默认资料，让未知问题看起来已研究完成。

若真实资料服务超时，应用尚未得到可解释的检索结果。此时应该按依赖故障处理，而不是诱导模型换同义词查询。权限拒绝也不能靠改写 query 绕过，重试策略要保留原授权主体和允许范围。错误文字只提供行动依据，不应泄露连接信息或内部堆栈。

步数上限是安全边界#

例子默认允许四次模型响应，正常轨迹只用两次。若把上限改为 1，工具可以已经返回，但模型还没得到最后一次组织答案的机会，函数会抛出预算耗尽异常。应用应把这种结果显示为未完成，而非截取最后一条工具文本充当最终答案。

实际程序还需要墙钟截止时间、工具调用额度和费用预算。模型轮次、工具数与图 super-step 是不同计数器：一轮可以请求多个工具，一次模型工具循环也会跨多个图步骤。为每个预算标明计数口径，告警才不会把合理并行误认成失控。

副作用应在哪里发生#

本章工具都是只读或纯计算，不会占用观测窗口。若以后增加 submit_proposal，执行器要在调用领域服务前检查申请版本、批准人和业务幂等身份。

执行阶段 收到的对象 可以作出的判断
解析请求 工具名、参数、调用 ID 是否是完整、已注册的调用
领域校验 申请编号、当前版本、服务端身份 该主体是否可提交该版本
副作用提交 稳定业务键 重试时返回原结果还是新建
结果回填 回执或明确失败 下一轮模型可据此解释什么

工具调用 ID 标识一次模型请求，业务键标识一次申请动作，两者不必相同。模型重新规划可能生成新 ID，但同一批准版本不能因此占用两次时段。系统提示中的“不要重复提交”无法提供这项保证。

离线运行本章示例#

保留原命令入口：

python3 examples/mini_agent.py

程序先运行内置断言，再打印 JSON 轨迹。正常角色序列是 user、assistant、tool、tool、assistant，其中两项工具观察分别包含资料记录和 total_s=1500。所有输入资料和模型响应都在本地构造，不需要密钥，也没有验证语言模型的推理能力。

停止条件要与任务进展一起看#

“没有工具调用”只意味着脚本或模型给出终止响应。资料是否够用，要从结果状态判断。未知问题应返回缺证据说明；已命中规则的申请才能给模拟时长建议。把这两条路径都跑一遍，比只检查正常答案更能发现默认回退掩盖缺失的问题。

若模型反复查询同一资料，比较本轮新增的来源和已尝试参数。没有新证据且预算下降，适合停止并请求澄清；补到了不同版本规则，可能有继续研究的必要。上限负责兜底，进展检查决定是否值得花掉下一轮。

手写例子的责任 框架中的相应位置 不应遗漏的应用责任

03

消息是运行时协议，不是聊天字符串

天文台助手收到两份数值都为 1500 的结果，不代表它们可以互换。一份可能是预算秒数，另一份可能是资料表中的探测器编号。消息需要记录说话者、请求身份、内容类型和附加数据，程序才有依据把观察送往正确位置。

LangChain 的消息对象提供这种结构。文本是其中一部分，空文本也可能承载完整调用；从显示界面上看不到的字段，同样可能影响执行、流式合并和恢复。

常见消息类型#

对象 在申请助手中的用途 不能据此推断的事
SystemMessage 设置可引用范围与输出要求 无法替代工具授权
HumanMessage 承载申请人的研究问题 不证明自述身份可信
AIMessage 生成建议或 tool_calls 不证明请求已执行
ToolMessage 送回预算与资料观察 不保证外部材料真实
AIMessageChunk 增量展示生成过程 不保证当前参数已完整

同一个对象还可能带响应元数据和 token 用量。应用可以用这些字段做诊断，但业务结论应有明确来源，不能用模型响应中的自信语气代替资料证据。

同一句文字放进不同消息，会改变含义#

“窗口为 1800 秒”若来自用户，是待核对的输入；若来自排班工具，是一项外部观察；若来自模型，是它生成的陈述。把它们拼成一段无角色文本后，后续节点便难以判断应优先信任哪项信息。

资料中还可能出现“请立即批准”的句子。即便这段内容由工具读回，也只是资料内容，不能提升为系统命令。保留 ToolMessage 的来源边界有助于隔离它，但最终仍需应用选择如何使用这些文字。

内容块与元数据#

观测研究可能同时使用文字规则和仪器图像。provider 对图像 URL、文件引用和音频的表示不同，消息的标准内容块用于减少业务与原生格式的耦合。不能假定每条 content 都是可以直接 .strip() 的字符串。

建议在进入草稿节点前做一次适配：提取允许的文本与图像引用，保留必要来源，其他 provider 特有数据留给观测层。遇到必须读取 additional_kwargs 的能力，把判断集中到适配函数，并用目标 provider 的小型合同测试固定行为。

usage 适合计费统计，响应 ID 适合排障；它们不会让 total_s 自动成为业务字段。业务预算来自工具或领域计算，模型 token 成本来自元数据，两类单位应分别记录。

工具调用必须闭环#

以下代码可在安装 langchain-core 后运行，构造一次资料查询的请求与结果：

from langchain_core.messages import AIMessage, ToolMessage

request = AIMessage(content="", tool_calls=[{
    "name": "lookup_observatory_rule",
    "args": {"rule_id": "SIM-TIME-4"},
    "id": "timing-rule-request",
    "type": "tool_call",
}])
observation = ToolMessage(
    content="教学记录 r1：逐帧读出 20 秒，固定校准 300 秒。",
    tool_call_id=request.tool_calls[0]["id"],
)
assert observation.tool_call_id == "timing-rule-request"

这段代码只创建协议对象，不执行检索。执行器应为本轮每个请求生成匹配观察，包括可恢复的失败。丢弃空 content 的 request 会让剩下的工具消息失去前置请求，实际 provider 可能据此拒绝下一轮输入。

调用 ID 为什么比工具名称更重要#

比较 6 帧与 8 帧方案时，模型可在一轮中请求两次 estimate_time。对应结果分别为 1500 秒和 1900 秒；用工具名作字典键会覆盖一项，而两个不同调用 ID 可以保留两份参数关系。

历史压缩也要维护这个关系。删去请求却保留结果，或者只保留两项结果中的一项，都可能造成未闭合工具轮次。对于仍需送给 provider 的近期消息，以完整交互为单位保留；更早已完成的研究可以变成带引用摘要。

artifact 不等于 content#

假设工具读取了 200 行模拟仪器参数，模型只需要其中两个开销值。content 可以放校准与读出的摘要，artifact 则保存结构化表或外部对象引用，供页面展示和后续程序使用。

模型没有看到 artifact，不意味着它不会进入 checkpoint、日志或调试事件。应优先保留小型版本化引用，避免把整份图像或表格反复写入状态。需要完整留档时，明确外部存储的访问控制与删除策略，不能仅靠消息字段名隐藏数据。

消息 reducer 为什么特殊#

普通列表相加只能追加。对话还会修正消息、删除指定消息和规范化不同输入形状，所以 LangGraph 用 add_messages 实现按 ID 的合并，MessagesState 为 messages 配好这个 reducer。

from langchain_core.messages import AIMessage
from langgraph.graph.message import add_messages

old = [AIMessage(id="budget-summary", content="预算待计算")]
new = add_messages(old, [AIMessage(id="budget-summary", content="模拟预算 1500 秒")])
assert len(new) == 1
assert new[0].content == "模拟预算 1500 秒"

稳定 ID 使这次返回表示修正。如果节点返回整份历史，新的无 ID 消息可能再次被分配身份，形成重复项。明确是修改已有消息还是追加观察，比把所有节点返回值统一做列表相加更重要。

流式 chunk 如何变成最终消息#

工具参数可能跨多个 chunk 才完整：一个片段含 {"frames":，下一个片段含 6,"exposure_s":，最后才出现 180}。在此之前，没有可验证的完整调用。

接收时点 可以展示什么 可以执行什么
获得工具名片段 正在准备预算计算 暂不执行
收到部分参数 可选的诊断预览 仍不执行
合并成最终调用 展示完整帧数和单位 校验与授权后执行

通常由框架负责 AIMessageChunk 合并，自定义转发层仍需区分增量和终态。不能把每个看起来可解析的局部 JSON 都运行一次；参数也可能尚未到齐或被后续片段补全。

上下文不是越长越好#

第十轮修改申请时，模型通常需要当前问题、最新规则、现行草稿和未解决意见，不需要每一次工具重试的完整堆栈。状态可以保存恢复所需数据，模型请求则由当前步骤选择一个较窄视图。

可把旧研究压成“规则 r1、计算条件、未核验事项”的摘要，保留最近完整消息交互；跨申请偏好从 store 按需检索。原始记录、模型上下文和用户事件分别有生命周期，不能用一个无限增长的 messages 同时承担所有任务。

用消息 ID 区分修正与新增#

草稿摘要从“待算”变为“1500 秒”，适合修正同一 ID；之后新增天气观察，应使用新 ID。若为方便总给所有 AIMessage 同一编号，add_messages 会覆盖先前消息，资料链可能被无声缩短。

检查上下文治理时，可以统计 ID 是否唯一、工具请求是否闭合、摘要能否追到规则版本。还应测试 artifact 不出现在模型请求中，以及其是否仍出现在其他出口。不同可见范围需要不同断言，单看页面文字不足以确认数据安全。

源码入口#

  • langchain_core/messages/base.py：检查内容、公共字段及序列化边界。
  • langchain_core/messages/ai.py：从最终调用与 chunk 合并代码核对执行时机。
  • langchain_core/messages/tool.py：定位结果 ID 和 artifact 的定义。
  • langgraph/graph/message.py：用同 ID、不同 ID、删除消息三种输入观察合并结果。

这些路径相对于归档仓库中的包目录。阅读时先找对象字段，再跟转换函数，避免把某个 provider 的原生消息结构当成通用合同。

04

工具调用：Schema、执行与结果回填

研究助手不应拥有一个可以任意执行代码的入口来计算简单预算。把能力收窄为明确参数的函数，模型更容易选择，应用也更容易校验和重放。工具设计要同时考虑模型如何理解能力，以及执行层究竟允许什么。

本章以教学预算工具和未来的观测申请提交为对照。前者是纯计算，后者会改变外部资源，两者即使用同一种 schema 表示，也不能采用相同的重试和授权政策。

从函数到工具#

安装 LangChain 后，下面的工具可独立构造并调用，不访问远程服务：

from langchain.tools import tool

@tool
def observation_seconds(frames: int, exposure_s: int) -> int:
    """估算模拟观测秒数，包含逐帧读出和固定校准，不验证真实排班。"""
    if type(frames) is not int or not 1 <= frames <= 30:
        raise ValueError("frames out of simulation range")
    if type(exposure_s) is not int or not 1 <= exposure_s <= 600:
        raise ValueError("exposure_s out of simulation range")
    return frames * (exposure_s + 20) + 300

assert observation_seconds.invoke({"frames": 6, "exposure_s": 180}) == 1500

名称给出动作，docstring 交代开销和限制，类型标注形成输入结构。若需要在公开 schema 中直接表达上下界，可以使用 Pydantic 参数模型；执行端仍应有领域校验。业务应明确能否接受字符串转数值等宽松转换，不能把框架默认转换等同于严格输入政策。

参数合法，与操作允许是两道门#

frames=6 和 exposure_s=180 结构合法，只表示可以进行计算。若工具改为提交申请，还必须确认当前调用者拥有该申请、批准的是同一版本、窗口仍可用。

可信身份应从服务端运行上下文注入，不能让模型填写一个 reviewer_id 就获得值班员权限。资料检索也一样：query 正确不代表能读其他课题组的未公开观测记录。公开参数只描述模型可选择的部分，身份和权限由应用服务控制。

BaseTool 也是 Runnable#

BaseTool 继承 RunnableSerializable，因此有 invoke、异步调用及配置传播表面。工具可以纳入同一条 trace，也可以在组件组合中被调用，但执行前后仍需处理参数转换、运行时注入和结果封装。

实际边界可按四个问题检查：注册表中是否有这个名称，输入是否满足合同，当前主体是否允许执行，返回值如何成为模型可读观察。模型生成的 JSON 只完成了提出请求这一项。即便它写出一个 Python 函数名，也不会绕过注册表直接获得函数引用。

ToolNode 解决什么#

ToolNode 识别末尾 AI 消息中的调用，找到注册工具，准备参数和注入依赖，执行后生成匹配的 ToolMessage。它还支持多个调用、异步执行、错误配置以及工具返回 Command 等路径。

预算和资料查询可以在同一轮分别完成。执行器负责每份结果的身份，应用负责决定哪些失败可以作为观察返回。配置错误处理前，应阅读当前版本的默认规则和参数，不要假定所有异常都会被吞掉或全部传播。

并行工具执行没有自动形成一个事务#

如果同一轮请求“保存申请”和“预留窗口”，前者成功、后者超时，ToolNode 不会自动撤销前者。工具并行只意味着任务可能同时运行，不提供两阶段提交。

这类复合操作最好由领域服务提供原子接口，或者明确记录每项状态并设计补偿。只读规则查询重试代价很低，资源预留则应使用申请编号和版本构造业务键。调用 ID 用于观察追踪，不能保证模型再次计划时仍使用同一 ID。

返回文本、对象还是 Command#

纯计算返回 1500 或带公式的对象即可，执行器会把适当内容包装成工具消息。资料查询可以返回摘要和 artifact，以免把整个手册送入模型。

当工具的结果确实就是图状态变化时，可返回 Command(update=...)，比如把核验后的 instrument_id 写回状态。但也要确保模型收到相应的工具观察；在标准消息图里，更新通常需要包含匹配调用 ID 的 ToolMessage。不要只改内部字段而留下悬空请求。

如果许多工具都能任意覆盖 approved、draft 和 status，控制流会变得难以追踪。批准资格更适合集中到审核节点，工具只报告验证事实，让状态写入者保持可辨认。

结构化输出不是普通工具#

最终研究结论可以约束为 total_s、sources、unknowns 等字段。Provider strategy 使用模型服务原生结构能力，Tool strategy 用特殊工具形式表达同一目标，create_agent(response_format=Schema) 可根据能力选择路径。

二者得到的是待业务检验的答案对象，不是外部申请回执。schema 校验通过表示字段形状符合要求，不能证明资料编号真实、预算公式正确或批准有效。应允许 unknowns 非空；强迫模型必须给出“可提交”会让信息不足被伪装成确定结论。

工具权限放在哪里#

静态白名单#

资料研究阶段只注册读取和计算能力。即便模型在不可信手册中看到“提交申请”的诱导，也没有对应可执行工具。减少能力面比在描述中反复提醒更容易验证。

静态集合适合阶段固定的应用。若同一 Agent 处理不同角色，不要为方便全量注册再寄望模型自行忽略敏感工具。

动态选择#

中间件可以按服务端角色和流程阶段选择当轮可见集合。未完成审批的申请不展示提交工具，已归档任务也不展示编辑工具。

动态筛选应记录决策依据，便于区分模型没有选择工具和工具根本不可见。请求文本里自称“我是台长”不能改变这个集合，缓存模型请求时也要考虑权限维度，防止复用高权限工具列表。

工具内部校验#

最终执行入口再次核对当前身份、对象版本和资源状态。这样即使上层路由或可见列表配置有误，也不会直接预留真实窗口。

授权拒绝应成为稳定的领域结果或明确异常，而不是返回“成功但忽略操作”。否则模型和后续状态会误以为申请已提交。拒绝消息给足解释即可，不返回其他租户对象的细节。

副作用与幂等#

未来提交申请时，可用类似 proposal:SIM-OBS-17:v2:submit 的键表达一次业务动作。真实系统应由服务端生成和核验它，并确保同一键、不同参数不会被当作正常重复。

最小执行记录包括业务键、参数指纹、批准版本、外部回执和确认状态。发生超时后，先按该键查询结果，再按远程服务合同决定重试。图里的 approved=True 不能证明外部服务已成功写入，外部成功也可能早于本地图状态保存。

通知调用超时后怎样核对实际投递结果#

申请提交后需要向值班人员发送通知。通知服务可能已发送，只是响应丢失；直接再发会产生两条提醒。

如果远程服务支持幂等键，重试应返回原通知 ID；如果只支持查询业务记录，先查询再决定；若两者都没有，就必须承认结果不确定，交由补偿或人工核对。不能把超时自动等同于未发送。通知内容还要绑定获批草稿版本，不能审批 v1 后悄悄通知 v2。

常见误区#

看似方便的设计 在观测助手中会发生什么 更窄的替代
把连接秘密放在描述里 发给模型或 trace 服务端注入连接

检查工具时，从一个最小合法输入和一个边界拒绝输入开始，再看未知工具名、超时与权限变化。选择质量和执行安全需要不同的验证，不能只测模型是否愿意调用。

05

Runnable 与 LCEL：统一调用表面

观测资料进入草稿前，常要经过规范化、检索、提示构造和解析。每个组件若使用不同的调用约定，组合代码就要反复处理异步、配置和回调。Runnable 把这些约定集中起来，LCEL 则提供组合表达式。

它适合组织数据怎样经过组件，不负责替应用保存隔天等待的审批状态。理解这个边界，可以把纯变换留在组件链里，把恢复位置留在状态图里。

一套接口#

方法或包装 观测助手中的用法 需核对的实现细节
invoke、ainvoke 处理一条规则查询 异步是否只是线程包装
batch、abatch 对一组资料查询取结果 是并发单调用还是服务端批量
stream、astream 展示草稿增量 组件是否真正产生增量
with_config 绑定运行标签和并发限制 子组件是否收到配置
with_retry 限次重试不稳定依赖 包住了多少已成功工作
get_graph 检查组合结构 可视化不等于恢复能力

默认接口会补足一些调用路径，组件可以覆写它们以提供原生能力。因此两个 Runnable 都有 batch，不意味着相同吞吐；一个受远程配额限制，另一个只是本地函数，增加并发的后果不同。

顺序与并行#

下面的代码只依赖 langchain-core，用真实 LCEL 组合处理一个申请标签：

from langchain_core.runnables import RunnableLambda

clean = RunnableLambda(lambda text: text.strip().upper())
inspect = clean | {
    "tag": RunnableLambda(lambda tag: tag),
    "is_simulation": RunnableLambda(lambda tag: tag.startswith("SIM-")),
}
result = inspect.invoke(" sim-obs-17 ")
assert result == {"tag": "SIM-OBS-17", "is_simulation": True}

| 形成顺序组合，字典中的分支被转换成并行组合。两个分支接收清理后的同一字符串，它们不会互相读结果。需要根据 is_simulation 决定标签展示方式，应在字典结果后再接一个步骤，而不是让分支依赖执行先后。

并行组合怎样形成下一步输入#

假设一条支路提取资料编号，另一条计算查询长度。两者都完成后，组合结果是具名字典，下游再读取字段。某分支先返回，不会自动触发依赖另一个分支的下游计算；这与“收到任意一个结果就继续”的竞速模式不同。

批处理则在另一维度上并行：同一个组件处理多个输入。测试时要分别检查输入输出顺序和错误行为，不把 batch 当作跨申请共享状态。提高 max_concurrency 可能减少本地等待，也可能让资料服务更早触发限流，需结合实际请求数测量。

配置如何传播#

Runnable config 携带 tag、metadata、callback、并发上限及可配置值等执行信息。顶层调用向子组件传播配置，可以把一次“研究申请”与其中的检索、模型、解析关联到同一 trace。

领域数据应放在输入或图状态中；身份和服务依赖适合放进可信 runtime context。不要仅从 trace metadata 读取 tenant_id 决定资料权限，因为观测标签和授权来源有不同的信任要求。

比如用 with_config(tags=["observatory-research"]) 标记调用很合理，把批准版本只写进 metadata 则不够：后续提交节点需要可检验、可恢复的业务字段。配置传播帮助诊断，不代替状态合同。

流式传播有条件#

用户想立即看到草稿，而资料检索可能必须一次性返回一个完整结果集。序列的增量能力取决于每一段能否消费和产出增量，不能只检查最前面的模型是否启用了 streaming。

排查时可记录各段首次产出的时间：provider 首个 chunk、解析器首个结果、应用首个事件、浏览器首次显示。若模型已经逐步产出而解析器最后才返回，网络层没有问题；若应用已发事件但浏览器等待整包，再查代理缓冲和客户端消费方式。

一个缓冲步骤会怎样改变流式体验#

模型逐步生成一个申请 JSON，解析器要求整个对象通过 schema 校验才返回。把它接入链之后，最终对象自然在末尾出现。这种等待适合预算、批准状态等需要完整校验的数据，不必为了逐字显示强行执行未闭合对象。

页面可以另外展示模型文字或进度事件，同时把结构化结果视为原子终态。不要将展示通道的“正在填参数”误当成工具可以执行的信号。选择哪个边界缓冲，是产品协议的一部分。

重试放在最小的不稳定边界#

以下为依赖 prompt、model、parser 已由应用构造的组合片段：

limited_model = model.with_retry(stop_after_attempt=2)
proposal_chain = prompt | limited_model | parser

它只重复模型调用，不会重复前面的资料准备。如果失败来自解析器，这个包装未必会触发重新生成；应按具体故障选范围，不能把所有失败都归为网络重试。

重试也要计入调用预算。一次逻辑模型步骤尝试两次，trace 中的真实请求和费用都可能增加。外层再设图节点重试时，必须计算嵌套上限，避免每层看起来都很小，组合后实际放大许多倍。

Runnable 与 LangGraph 的连接#

图节点可以接收普通函数或 Runnable，编译后的图也提供 Runnable 表面。这允许在一个草稿节点里调用 LCEL 链，在外层继续使用 invoke、stream 等方法驱动整图。

节点返回值仍须遵守状态图合同。链若产出一个字符串，节点通常要映射为 {"draft": text}；不能因为它是 Runnable，就自动变成正确的 partial update。callback 和配置可以贯穿两层，业务字段怎样合并仍由图 schema 决定。

何时用 LCEL，何时用图#

查询标签规范化、文档拼接和固定解析，可以留在一个无环组合里。需要拒绝后回到修订、保存中间状态、等待值班员确认，或分别恢复失败专家时，状态图能把这些依赖表达出来。

粒度不必与每个函数一一对应。一个节点内部包含几次可安全重放的纯变换通常没有问题；若某段工作值得独立重试或恢复，再拆成节点。这样既能保留组件组合的简洁，也不把重要业务阶段藏进深层 lambda。

重试整条链，为什么可能重复已经成功的工作#

设查询资料成功后模型超时。重试外层整链会再查一次；资料服务收费或结果会变时，第二次并不等价于沿用第一次观察。若前面还执行了窗口预留，重复调用会成为副作用风险。

可以将已确认资料存入状态，再只重试生成步骤，或者把最不稳定的调用独立包装。Runnable 不会分析函数副作用来自动选最安全的范围，范围需要根据故障和恢复需求确定。用一个计数器记录测试中各组件执行次数，便能看出重试到底重复了什么。

源码入口#

  • langchain_core/runnables/base.py：从序列和并行组合的调用方法追输入形状。
  • langchain_core/runnables/config.py：检查配置合并与子调用传播。
  • langchain_core/runnables/retry.py：核对尝试次数和捕获条件。
  • langgraph/_internal/_runnable.py：查看图如何适配 callable 与 Runnable。

可以先运行申请标签的小例子，再替换其中一支为故意抛错的函数，观察异常与重试边界，而不必接真实模型。

06

create_agent 到底创建了什么

观测规则问答通常符合一个循环：模型缺资料时请求工具，看到结果后继续研究，材料够了就回答。create_agent() 把这种常用形状和组件协议组装成图，返回 CompiledStateGraph。工厂调用本身不会完成研究，也不会因为返回值叫 Agent 就自动保存所有运行数据。

先区分构建和执行，才能判断工具未出现、审批未暂停或结构化结果缺失，应从哪一层排查。

默认图形#

把本章默认循环画成请求与观察的往返表，而不只看节点名称：

当前执行位置 本次产物 下一次被调度的工作
入口 输入消息进入状态 model 读取当前上下文
model search_notes 与预算调用 tools 处理这一轮请求
tools 两项带调用 ID 的观察 model 重新读取新增证据
model 不含普通待执行调用的回答 正常结束，或由已配置策略继续处理

这是省略中间件与结构化输出分支的教学形状。真实图会依据配置增加 hooks 和策略节点，无工具时也无需普通 tools 循环。判断当前图形应看工厂输入和编译结果，而不是假定每个 Agent 都有完全相同的边。

工厂阶段做了什么#

工厂将模型、工具、输出 schema 和中间件声明整理成可编译图。字符串模型标识需要初始化，字符串系统提示转换为消息，普通函数转为工具；供应商内置工具与应用执行工具的处理路径并不完全相同。

接着收集中间件的工具、状态字段和 hooks，组合模型与工具调用 wrapper，建立模型节点、工具节点及路由。最后把 checkpointer、store 和中断配置传入编译。这个过程决定能力集合和控制结构，不决定每次生成的具体参数。

定位问题时可列一份构建清单：注册了哪些工具，输出策略是什么，哪些中间件增加了节点，是否真的绑定 saver。只设置 thread_id 而未提供保存实现，无法得到期望的会话恢复。

工厂构建发生一次，模型选择发生多次#

同一个编译图可用于多个独立 thread。模型每次运行时读取当前消息，可能查询 SIM-TIME-4，也可能直接解释已有结果。产生新的调用只在既定能力范围内选择，不会把未注册的提交函数变成工具。

因此，工具名不存在应查构建输入，工具可见但从未选择应查描述与上下文，参数合法却被拒绝应查领域授权。把这些情况统一处理成更强烈的系统提示，会掩盖真正失败位置。

middleware 的四种作用#

改模型请求#

中间件可以在调用前选择本轮消息、系统提示、模型或工具列表。比如资料研究阶段只展示检索与估算，提交阶段才可能展示写操作。

这种变化应基于服务端可信阶段，不接受用户文字直接改权限。裁剪消息时还需保持近期工具交互闭合，不能删去请求却保留结果。

包模型调用#

wrapper 可记录请求、设置限额、尝试 fallback 或缓存结果。它围绕一次模型调用组织行为，不必成为独立的业务节点。

失败后换模型要重新核对工具与输出能力，不能只替换模型名。缓存键也需要覆盖影响结果的资料版本和策略，不能把旧规则下的建议返回给新申请。

包工具调用#

统一工具 wrapper 适合错误分类、尝试次数、审计与审批门控。它可以阻止未满足前置条件的请求，也可以将允许修正的参数错误转换为观察。

领域服务仍应再次授权。wrapper 配置错了不该导致跨课题组读数据，缓存命中也不能跳过当前对象权限检查。

在循环前后执行#

before/after model 或 agent hooks 可维护统计、摘要或业务字段，其中部分会形成图节点。这会改变状态更新与恢复的边界，不能把它们都当成无状态装饰。

如果一个 hook 写 store 或通知外部服务，应审查其重放行为。名字叫 after 并不表示它有不可重复执行保证。

wrapper 的顺序会改变你观察到什么#

设有缓存、授权检查与调用计数。缓存放在最外层且直接返回时，内层可能根本不执行；若授权也在里面，权限撤销后仍可能看到旧结果。安全检查应覆盖缓存命中路径。

再比较重试与计数：计数在外、重试在内，记录一次逻辑调用；计数在内则可能记录每次真实尝试。两种指标都有用，但必须命名清楚。用“缓存命中”“第一次超时第二次成功”“授权拒绝”三个输入分别检查 wrapper 顺序，比只看正常调用更有效。

context、state 与 store#

位置 本场景内容 如何变化
State 消息、当前草稿、资料引用、修订号 节点增量经 reducer 合并，可进入 checkpoint
Runtime context 可信课题组身份、连接依赖、运行设置 每次调用注入，通常按只读依赖使用
Store 跨申请的已确认仪器偏好或规则索引 由应用显式读写，独立管理生命周期

context_schema 描述运行时依赖形状。快照中的 config_schema 已有弃用提示，新实现应围绕 context 组织注入。配置中的 thread_id 则继续用于定位恢复实例，它不能替代授权主体。

如果批准状态只在 context 中，下一次请求可能缺失；如果数据库连接放进 state，序列化和恢复会失败或保存无意义对象。按用途选择容器，能避免把持久化当成任意 Python 对象快照。

结构化输出的选择#

response_format=Schema 允许工厂依据模型能力选择原生 ProviderStrategy 或工具形式的 ToolStrategy；显式策略则需要调用方承担兼容性判断。不同策略可能改变内部请求与路由，不能把所有工具形状都当成外部副作用。

结果在 state 的 structured_response 中读取。比如结论对象可以含 total_s=1500、资料编号和未核验事项。字段校验只能约束类型和声明规则，真实证据仍需核对，不能从 schema 通过直接推出申请获批。

高级工厂并没有消除图#

以下为应用已提供模型、工具和存储后的构建片段：

from langchain.agents import create_agent

agent = create_agent(
    model=chat_model,
    tools=research_tools,
    system_prompt="只根据允许的观测资料提出建议，列出尚未核验的条件。",
    checkpointer=saver,
    store=knowledge_store,
)

运行时仍使用图的 thread、stream 和 checkpoint 语义。动态 interrupt() 暂停后通过 Command(resume=...) 提供决定；如果用 interrupt_before 设置静态断点，继续执行通常传 None，不能把两种暂停混为一谈。

工厂图也可以被父图作为研究节点使用。外层负责固定预算与审批，内部 Agent 自主补资料，便能在不重写工具循环的前提下加上业务阶段。

create_deep_agent：预装好的 harness#

当研究需要工作文件、长任务清单、技能加载和窄任务委托时，create_deep_agent 提供一组现成组合。它继续建立在 LangGraph 上，默认能力与签名则取决于单独安装的 deepagents 版本。

在天文台场景中，是否需要文件工具取决于资料处理方式。只查两条规则时，整套 harness 可能多余；需要生成多份研究附件时，才值得检查 backend、摘要和子 Agent 的组合。第 16 章会逐项讨论，不把默认工具等同于默认安全。

何时离开 create_agent#

如果要求预算计算完成后必须独立核验，再由值班员批准，且任一失败有固定结束状态，显式 StateGraph 更容易检查依赖。模型无需成为每一个阶段的路由中心。

如果变化只是更换 prompt、限次重试或增加一种最终 schema，先使用工厂配置和中间件。自定义图接管的是控制结构和恢复责任，不应仅为获得更多节点名称而增加。

结构化结果应该从正确字段读取#

自然语言说“可以安排”，不等于 structured_response 中所有条件满足，更不等于人工批准。调用方应读取约定字段，再执行独立的数值、引用和权限判断。

当资料缺少滤镜配置时，输出合同应允许缺失和未知，而不是强制一个批准布尔值。否则模型容易为了满足格式给出错误确定性。区分研究结论、审批结果和真实提交回执，可以防止三个不同状态挤进一个 approved 字段。

  • langchain/agents/factory.py：从返回类型、节点创建和条件路由追组装。
  • langchain/agents/middleware/types.py：检查 hooks 与 wrapper 合同。
  • langchain/agents/structured_output.py：核对 schema 策略和结果位置。
  • langgraph/prebuilt/tool_node.py：追普通工具请求的执行与回填。

StateGraph：状态、节点、边与 reducer

研究流程里，资料是累计的，草稿是可替换的，批准必须对应当前版本。若把这些字段都当成普通字典写入，串行正常例子可能运行，但并行检索和拒绝修订会暴露含义冲突。

StateGraph 要求把状态形状、节点结果和合并规则写出来。节点读取一份快照，返回本次变化，运行时再形成下一份快照。明确每个字段怎样变化，比增加更多节点更能改善可解释性。

StateGraph 是构建器#

以下完整例子演示固定预算步骤，不使用模型或网络：

from typing import TypedDict
from langgraph.graph import START, END, StateGraph

class BudgetState(TypedDict):
    frames: int
    exposure_s: int
    total_s: int

def budget(state: BudgetState) -> dict:
    return {"total_s": state["frames"] * (state["exposure_s"] + 20) + 300}

builder = StateGraph(BudgetState)
builder.add_node("budget", budget)
builder.add_edge(START, "budget")
builder.add_edge("budget", END)
compiled = builder.compile()
result = compiled.invoke({"frames": 6, "exposure_s": 180})
assert result["total_s"] == 1500

构建器尚不能执行，compile() 才生成运行对象。TypedDict 描述形状，不等于完整运行时领域校验；真实输入仍要验证正数、单位和上界。本例刻意聚焦状态更新，不代表任意帧数都有效。

State、Input 与 Output 可以不同#

公开输入可只包含申请问题和观测参数，内部状态还保存资料、修订号与失败原因，公开输出只暴露建议和本地回执。用不同 schema 可以减少接口耦合，避免用户提交内部状态字段。

这不构成所有出口的保密保证。values 流、调试信息或 trace 可能包含更宽的状态。若内部含未公开课题编号，应在用户事件适配层做字段白名单，同时控制 checkpoint 与日志访问，不把 output schema 当成统一脱敏器。

默认 reducer 是覆盖#

draft: str 使用普通单值语义，后续修订覆盖当前草稿很自然。但两个并行专家若都写 draft，同一步里没有合理的单一赢家，运行时通常会报告并发更新错误。

修复方法取决于含义。两份独立意见应放入不同字段或可累计结果集合；一份最终草稿应由下一步聚合节点选择生成。不要用“谁先结束”“谁最后返回”表达权威性，也不要为了消除异常给所有字段添加加法 reducer。

reducer 是二元合并函数#

资料记录可以声明为累计列表：

from operator import add
from typing import Annotated, TypedDict

class EvidenceState(TypedDict):
    notes: Annotated[list[str], add]

运行时用旧值和本次更新计算新值。追加 reducer 要求节点只返回新增记录，返回 old_notes + new_notes 会让旧内容再累积一遍。纯函数、确定性以及适合并行合并的代数性质有助于重放；列表追加虽然结合，但不交换，展示顺序仍应按稳定资料编号整理。

空列表对追加字段表示没有新增，不能表示清空。需要替换累计值时，当前 API 可用 Overwrite 绕过 reducer，或者设计明确的重建步骤；同一步多处覆盖仍应避免。清理动作要有独立语义，不依靠含糊空值。

用两个检索节点手算一次合并#

设旧资料为 [SIM-REQUEST-1]，规则支路返回 [SIM-FILTER-2]，预算支路返回 [SIM-TIME-4]。合并后应有三个来源，业务应按来源身份去重和排序，不能把列表首项自动解释成最重要证据。

节点返回方式 合并后的记录数量 原因
各支路只返回新资料 3 一份旧资料加两份更新
各支路返回旧资料加新资料 5 旧资料被追加了两遍
两支路写同一个无 reducer 字段 无有效结果 单值 channel 拒绝并发更新

这三种行为来自更新合同，与检索结果是否正确是两个问题。测试除了看文本，还应断言来源集合和数量。

Node 只是函数，但签名有层次#

节点最少接收 state，返回字典增量。需要业务身份或连接时可接收 Runtime[Context]，需要运行配置时使用 Runnable config。依赖从签名中可见，测试便能提供固定上下文，而不必修改全局变量。

节点粒度可以按恢复成本判断。数值格式化不值得单独保存，外部资料查询可能值得独立重试，生成草稿与等待批准则应分开。节点越粗，失败后重复工作越多；越细，schema、调度和版本兼容的维护面越大。

Edge 表示调度，不表示数据复制#

预算节点到审批节点的边意味着前者完成后可激活后者，审批读取的是共享状态视图，并非沿边传来一个私有字典。分支输入若需要独立载荷，应显式使用相应任务机制或转换节点。

多个出边可安排同一步并行工作。同一步任务读取一致的前步快照，某支路先算出 total_s，另一支路也不会立即读到它。需要先算后读时，应表达先后依赖。

边的含义是安排工作，不是传递专属字典#

规则检查与时长检查都依赖原申请，可以并行；最终结论依赖两者，应明确等待全部完成。add_edge(["rules", "timing"], "conclude") 表达共同依赖，比单独添加两条普通入边更直接。

如果两支路长短不同，尤其不能仅凭图上两条线就推断聚合只执行一次。用节点执行计数和各步输入断言，确认结论节点在两项结果都可见时运行，避免产生早到的不完整建议。

compile 做的不只是画图#

编译会校验节点和边引用，从状态注解建立 channel，将节点及路由接到触发和写入机制，并绑定保存、store、缓存和中断配置。得到的是可以执行的 Runnable 图，而不是一张图片。

编译后再给原 builder 增加节点，不应期望已存在的运行对象随之更新。部署时应构建新图并管理版本；恢复旧 thread 时，节点名和字段合同仍要匹配。静态检查能发现部分结构错误，不能证明业务分支都正确。

一个状态设计检查表#

可以为申请写一份字段合同，而非笼统规定所有数据都入 state：

字段 写入者 合并含义 生命周期与出口
notes 检索节点 追加新版本化来源 草稿和审批所需，可限量
total_s 预算节点 单值替换 当前参数的计算结果
draft 草稿与修订节点 当前版本覆盖 审批预览可见
revision 生成及修订节点 单调增加 绑定批准与回执
receipt 本地发布节点 单值确认结果 最终输出，不冒充远程回执

还应为每项说明最大规模、删除方式和敏感程度。若两个写入者给字段不同含义，先拆开字段再考虑合并，避免把语义冲突交给 reducer 隐藏。

状态字段越多，恢复合同越大#

保存整份仪器手册有利于重现，却放大每一步序列化成本；只存 URI 更小，却可能在恢复时读到新版。可用资料编号、revision 和内容指纹固定证据，按审计需求决定是否另行留存原文。

字段改名或语义变化也会影响旧 checkpoint。window_s 若以后改成分钟，数据仍可反序列化，却会导致严重预算误判。版本验证必须运行旧状态下的计算和路由，不能仅测试“能加载”。

  • langgraph/graph/_branch.py：核对条件边的目标处理。

08

路由、循环与 Command

6 帧方案需要 1500 秒，8 帧方案需要 1900 秒，两者面对 1800 秒窗口应走不同路径。状态图的路由把这种结果变成调度决定：预算满足才等待审阅，预算超限则停下解释或请求新参数。

下一步由状态决定时，必须明确决定读取的是哪个值、是否已经更新，以及进入循环后靠什么停止。否则图虽然有条件边，实际仍可能使用旧判断或无限修订。

固定边与条件边#

资料搜索完成后总要生成草稿，可以使用固定边；草稿形成后是否进入审批，则适合条件边。以下为 builder 和相应节点已经定义后的片段：

builder.add_edge("search", "draft")

def after_draft(state):
    if state["status"] == "needs_evidence":
        return "halt"
    return "review" if state["total_s"] <= state["window_s"] else "halt"

builder.add_conditional_edges(
    "draft", after_draft, {"review": "review", "halt": "cancel"}
)

路由只解释已写入状态，不在这里另查排班或发送通知。这样同一输入能得到相同选择，状态历史也能解释为何走到某条分支。真实资源状态若需要再核验，应作为明确节点，而非隐藏在路由函数里。

Command 合并更新与跳转#

审核决定同时改变 approved 和后继位置时，用 Command 可以把这项决定放在一起。以下片段假定 decision 已由可信外部输入获取并校验：

from typing import Literal
from langgraph.types import Command

def apply_decision(state, decision) -> Command[Literal["publish", "revise"]]:
    accepted = decision["approved"]
    return Command(
        update={"approved": accepted, "feedback": decision.get("feedback", "")},
        goto="publish" if accepted else "revise",
    )

这展示更新和调度表达，不是可直接注册的完整节点，因为应用还要负责提供 decision。第 14 章的真实节点在内部调用 interrupt() 获得它。类型参数标明目标，有助于检查和可视化，不代替运行时业务校验。

更新与跳转为什么应来自同一个决定#

拒绝 v1 后，状态应写 approved=False 并进入修订。如果另一处路由仍读取旧的 approved=True，就可能错误发布。让更新和跳转使用同一份已验证决定，能减少这种分离判断。

goto 不会抹去原有静态边。若 review 同时有通向 publish 的固定边，又返回 goto="revise"，两个目标都可能被调度。测试时应断言拒绝分支没有发布，不只断言修订出现了。

Send 表示动态 fan-out#

一份申请可能附带任意数量的参考记录，适合为每条记录安排一个核验任务。下面是已定义 check_record 节点后的路由片段：

from langgraph.types import Send

def fan_out(state):
    return [Send("check_record", {"source": source, "proposal_id": state["proposal_id"]})
            for source in state["sources"]]

每个任务只拿当前资料和申请身份，避免复制整段会话。结果应带来源 ID 写入可合并字段，再由下一步按来源排序、去重和检查缺项。任务数量为零时也应定义行为，比如直接输出证据不足，不能假定聚合节点必定被唤醒。

输入集合 子任务载荷 聚合必须核对的内容
2 个规则来源 各自编号与版本 两项都已返回且版本正确
1 个被拒绝来源 拒绝原因与来源身份 是否允许缺项继续
空来源集合 没有动态任务 另一路径表达证据不足

这张表强调基数和完成状态，动态并行并不自动给出“所有证据齐全”的业务结论。

循环要有业务不变量#

修订循环会消耗版本和预算。示例只允许审阅 v1、v2、v3，拒绝第三版后进入 review_limit，不再生成 v4。状态中始终保持已研究资料不因单纯修订而重复追加。

next_node = "revise" if state["revision"] < 3 else "cancel"

实际循环也可以跟踪待核验来源、已尝试查询、费用或截止时间。每轮必须说明什么在向停止推进，不能只依赖模型宣称完成。框架 recursion limit 保护图步骤，业务上限则给出用户可理解的原因。

修订循环需要一个可观察的前进条件#

拒绝 v1 的意见若是“注明尚未核验目标高度”，修订节点应保存这项意见、增加 revision，并写入新草稿。没有修改意见或新资料时，反复生成相同文本没有研究收益。

判断进展可比较来源集合、草稿指纹和未解决项。三次拒绝后结束，并不表示申请失败的所有原因都已查清，而是当前修订额度耗尽。将 published_locally、needs_evidence、over_budget 和 review_limit 分开，用户和测试才知道流程停在哪里。

并行不是竞态自由#

规则节点和时间节点同一步运行时，都只能读取前一步状态。规则节点不会因为快一些就让时间节点看到新字段，所有本步写入等合并后才对下一步可见。

reducer 解决的是写入合并，不能自动解决领域冲突。两个专家对可行性一赞一反，应保存两份独立判断和证据，让聚合节点显式处理。把布尔值改成列表只能保住信息，仍需定义怎样作决定。

错误路由与异常不是一回事#

needs_evidence 表示搜索已完成但无匹配，over_budget 表示计算得到超限结果，都适合正常返回并路由。连接断开则可能尚未获得结果，应保留故障和有限重试语义。

当人必须作选择时使用中断；当权限被拒绝时，不应通过不断换工具绕开。分类决定图如何继续，也决定观测如何计数。把服务故障伪装成无资料，会让模型错误解释成知识缺口；把正常超预算抛成系统错误，又会制造无意义重试。

父图与子图的跳转#

子图可以通过 Command(graph=Command.PARENT, ...) 将更新和控制交到父图。适合明确 handoff，但更新的共享字段需要父层可接受的合并语义，不能假定子图能任意重写父状态。

研究专家通常只需要回传 findings，父图负责预算与审批。若没有正式控制权转移需求，输入输出映射更容易测试。跨图跳转应少量且有明确目标，避免读一个局部函数却无法知道它会跳到整个应用的哪里。

错误分支与异常恢复分别表达什么#

假设子图核验来源 A 成功、来源 B 超时。父图可以保留 A，仅重试 B；也可以以资料未齐终止。无论选择哪条，都要区别“B 没支持结论”和“B 尚未被观察”，否则聚合得到虚假的反对证据。

跨图时还应把失败身份带回来。只返回 failed=True 无法判断该重试哪个来源，直接把子图全部历史复制到父层又扩大上下文。窄结果对象可以同时包含来源、完成状态和失败类型，使路由有足够依据。

源码入口#

  • langgraph/types.py：阅读 Send、Command 和动态中断的字段定义。
  • langgraph/graph/_branch.py：跟踪路由返回目标如何转换成调度信息。
  • langgraph/graph/state.py：对比固定边和等待多个来源的边。
  • langgraph/pregel/_algo.py：观察任务准备和写入应用的时序。

用一次批准、一次拒绝和一次预算不足的轨迹比较，会比单看图像更容易发现多余固定边或缺失结束状态。

09

Pregel：图在运行时如何前进

观测规则检查已经返回，时间检查还在运行。此时最终结论能否读取前者的新结果？答案取决于任务所在的 super-step，而不取决于哪个线程更快。Pregel 用明确的执行和更新边界组织图，StateGraph 则把这些细节包装成状态、节点和边。

本章不要求直接写底层 actor。目标是能解释一次并行执行的可见性，以及失败后为何不能把 Python 调用栈当作恢复依据。

整体同步并行（Bulk Synchronous Parallel）#

BSP 将运行分成同步步骤。用教学申请画出两个步骤的状态截面：

时间截面 规则任务 时间任务 全局可见状态
步骤 k 规划后 等待执行 等待执行 两项结果均未知
步骤 k 执行中 已产生规则结果 仍计算预算 仍是步骤 k 的输入快照
步骤 k 更新后 写入已合并 写入已合并 规则 r1，预算 1500 秒
步骤 k+1 聚合任务读取结果 无需重算 可以形成待审草稿

表中的快慢是教学推演，不是性能实测。关键是规则任务提前完成不改变本步其他任务读取的快照。

规划（Plan）#

规划阶段依据输入和 channel 的版本、触发关系准备可运行任务。节点存在于图里不代表每次都执行，未被激活的审核或取消节点不会自动运行。

排查“节点没跑”时，先看前一步触发了什么和当前 next，而不是直接怀疑执行器漏调函数。输入、普通边和动态发送都可能产生任务，但路径需要符合编译后的触发机制。

执行（Execution）#

选中的任务运行，并把结果作为待应用写入记录下来。执行可能涉及同步、异步或并发，某项失败或超时会影响本步推进。运行时不会让其他同一步任务读取这项任务尚未合并的更新。

节点若直接改外部数据库，外部系统仍可能立即可见；BSP 的隔离针对图 channel，不是所有外部资源。这也是不能用并行 state 语义推断外部事务的原因。

更新（Update）#

执行结果按 channel 规则合并，形成后续可见值并影响下一批任务。默认单值字段遇到多写入可能报错，加法累计字段则按 reducer 处理。

当没有后续可运行工作，运行可结束或处于等待外部恢复的状态。应用要区别终态与暂停：两者都可能令一次请求返回，但暂停 thread 仍有待恢复任务。

actor 与 channel#

底层 PregelNode 组织可执行逻辑及其读取、订阅和写入关系。Channel 管理值与更新；StateGraph 编译器根据字段和路由建立这组对象。

Channel 可类比的用途 使用时要留意
LastValue 当前草稿或单项预算 不接受同一步多份竞争写入
BinaryOperatorAggregate 累积资料记录 reducer 的代数和去重含义
Topic 发布多个观察 是否跨步累计及读取形状
EphemeralValue 临时触发信息 不能当成长期业务存储
DeltaChannel 增量持久化的累计值 beta 及恢复格式约束

日常应用通常只需 schema 和 reducer。直接选择特殊 channel 之前，应确认默认语义确实无法满足需求，而非为了避免设计清楚字段。

为什么本步写入不可见#

若时间任务有时能看到新规则、有时看不到，结果就受网络和线程调度影响。BSP 固定读取边界，使这项依赖必须写成跨步骤关系。规则决定开销时，应先核验规则，再执行时间计算；两者彼此独立时才适合并行。

这种可见性不保证所有结果顺序都天然稳定。累计列表仍要自行按业务身份排序，外部查询也可能得到变化的数据。运行时固定的是步骤边界，重现业务结果还需要纯 reducer、版本化来源和明确输入。

两种并行更新的不同结果#

设 checked=0，两项核验都返回增量 1。若字段使用加法累计，更新后为 2；若字段是默认单值，两个写入不能简单取“最后一个”，会构成并发更新冲突。

但若返回的是两项 eligible=True/False，相加毫无意义。应把规则核验和预算核验保存在独立字段，聚合时要求二者均满足，并保留否决原因。相同运行机制需要不同合并设计，channel 不会猜业务意图。

运行循环中的关键对象#

阅读源码时可把问题分配给对象：入口在 Pregel.invoke 或流式方法；PregelLoop 管运行上下文和步骤；任务准备逻辑确定本步做什么；PregelRunner 执行；apply_writes 让结果成为 channel 值；保存与事件出口随后按当前持久化模式推进。

这不是承诺每个流事件都严格晚于数据库持久提交的统一时间线。同步、异步持久化及事件类型会影响可观察时序，需在目标版本和配置下核对。看到一个节点更新事件，不能直接断言外部系统和检查点已经形成原子提交。

checkpoint 为什么适合放在步骤边界#

步骤更新完成后，可以描述一份一致状态和后续任务。恢复只需要读取这些值与任务信息，不必尝试还原正运行到某一行的 Python 线程。

保存策略仍影响崩溃窗口。若副作用已发生但对应完成状态尚未可靠保存，恢复可能重新执行相关工作。持久化保证的是图状态可延续的边界，不会自动去重资源预留或通知。

步骤边界不是跨系统事务边界#

设申请服务已返回 reservation-17，进程在本地图状态持久化前退出。旧 checkpoint 不包含这个回执，但远程窗口已被占用。重启后提交节点再运行，必须按同一业务键查询或重用结果。

并行恢复还可能利用已保存任务的 pending writes，避免重复成功支路。实际重跑范围由任务边界和保存结果决定，不宜简化为“全部重跑”或“成功项永不重跑”。测试应注入失败验证目标场景，业务操作始终保持可重放。

recursion limit 计算什么#

这里的限制针对图 super-step，不是 Python 递归层数，也不是所有节点执行次数。两个并行核验处于同一步，模型和工具来回则通常跨多步。

申请修订应另设版本上限，资料研究另设调用预算。把 recursion limit 从较小值调到很大，无法证明循环合理，只扩大最坏开销。记录最终结束原因和已用业务额度，比单独统计是否触发框架限制更有诊断意义。

DeltaChannel 的取舍#

长会话的累计资料可能在每步 checkpoint 中反复写入。DeltaChannel 旨在持久化更新增量，再按需要重建累计值。对于每次只增加一个小观察、历史很长的字段，写入量可能降低；实际收益要测量，不能从概念直接推算。

代价是读取重放成本、批量 reducer 约束和格式兼容。快照将其标为 beta，旧运行时未必能理解新格式。部署前要准备带真实更新分布的恢复测试和回退策略，而不是直接替换所有消息字段。

增量存储为什么对 reducer 提出更高要求#

假设有更新序列 a、b、c，一次合并三项与先合并 a、b 再合并 c 应产生相同业务值。批处理分组变化若影响结果，重建就不再可靠。reducer 里读取当前时间、产生随机 ID 或查询外部规则，都会使旧更新在未来重建时可能变样。

可以用固定输入序列比较多种分组，并核对完整快照与增量恢复的最终结果。列表去重还要定义稳定键与版本冲突政策，不能依赖恰好到达的先后顺序。优化存储前先把这些合同固定下来。

直接用 Pregel 吗#

大部分观测助手需求在 StateGraph 或 Functional API 层就能表达。直接 Pregel 更适合研究 actor/channel 行为、开发特殊运行时组件，或验证框架机制。

如果目的是“预算先算、人工后批”，下沉只会增加接线工作。先用高层图表达业务不变量，只有无法表达且已有最小反例时再考虑低层接口。

源码入口#

  • langgraph/pregel/main.py：从调用、流式和运行参数进入。
  • langgraph/pregel/_loop.py：跟步骤推进、保存和恢复状态。
  • langgraph/pregel/_runner.py：观察并发任务与失败处理。
  • langgraph/pregel/_algo.py：检查任务准备及写入应用。
  • langgraph/channels/：对照不同字段更新合同。

带着“本步谁读旧值、何时合并、失败留下什么”三个问题查找，会比从入口顺读全部实现更容易得到可验证结论。

检查点与 Store：两种记忆边界

申请 A 等待批准时，系统需要记住待审草稿和下一步任务；申请 B 开始时，系统可能还要读取同一课题组常用的滤镜偏好。前者属于一次流程的恢复，后者属于跨流程的业务数据，不能用一个含糊的“记忆对象”代替。

Checkpointer 与 Store 分别服务这两个范围。它们都可以使用内存或持久实现，但跨 thread 共享和跨进程存活是不同维度。选择接口后，还要决定数据如何确认、更新、检索和删除。

checkpointer 保存什么#

下面的片段假定 builder 已定义状态和节点：

from langgraph.checkpoint.memory import InMemorySaver

saver = InMemorySaver()
graph = builder.compile(checkpointer=saver)
address = {"configurable": {"thread_id": "proposal-SIM-OBS-17"}}
paused = graph.invoke({"question": "研究 Halpha 申请", "notes": []}, address)
snapshot = graph.get_state(address)

运行时利用 channel 值、版本、任务和元数据等信息描述恢复位置。应用看到的 StateSnapshot 可用来检查当前值、待执行节点及相关任务，而不是只找一份聊天文本。

thread_id 是寻址的一部分。每次换新 ID 会启动不同实例，所有用户共用一个 ID 则可能混合状态。服务端应先核对申请归属，再映射到 thread，不能把客户端提交的任意 ID 当成访问许可。

store 保存什么#

比如某课题组确认今后的模拟研究默认使用中文、常选 Halpha，可保存为一条版本化偏好：

namespace: ("observatory", "team-cedar", "preferences")
key:       "proposal-defaults"
value:     {"language": "zh", "filter": "Halpha", "confirmed": true}

namespace 划分访问和组织范围，key 标识同一条业务记录。新申请会显式查询这项偏好，旧 thread 的待审位置却不能从偏好里恢复。Store 不会自动从聊天中判断哪句话应长期记住，也不会自动把一次临时方案提升为默认值。

写入策略要说明确认来源、覆盖规则和失效条件。偏好被改正时应更新同一业务键，而不是每次追加一条互相冲突的自然语言记忆，再依赖相似度猜哪条最新。

Runtime 与 context_schema：节点如何访问 store#

身份来自可信调用上下文，store 由编译图注入。以下为一个可用于已配置 store 的节点片段，输入字段与节点由应用接入：

from dataclasses import dataclass
from langgraph.runtime import Runtime

@dataclass(frozen=True)
class Context:
    team_id: str

def load_defaults(state, runtime: Runtime[Context]):
    if runtime.store is None:
        raise RuntimeError("preference store is required")
    namespace = ("observatory", runtime.context.team_id, "preferences")
    item = runtime.store.get(namespace, "proposal-defaults")
    return {"defaults": item.value if item else {"language": "zh"}}

构建时使用 StateGraph(State, context_schema=Context)，编译时传入 store=store，调用时传 context=Context(team_id=trusted_team)。其中 trusted_team 由应用认证得来，不是模型选择的字符串。thread 地址继续放在 config，用于恢复，与业务身份分开校验。

连接、用户身份等通常只在本次运行使用，不宜直接序列化进 state。节点输出 defaults 后，是否保存到 checkpoint 取决于状态设计；若希望审批依据固定，应保存本轮读取的偏好版本，而非每次恢复悄悄换成当前值。

store 自带语义检索#

带 embedding 索引的 Store 可以按 query 检索相关值。下面构造一个两维教学 embedding，用来说明接口，不代表真实语义模型或检索质量：

from langgraph.store.memory import InMemoryStore

def teaching_embed(texts):
    return [[1.0, 0.0] if "Halpha" in text else [0.0, 1.0] for text in texts]

store = InMemoryStore(index={"embed": teaching_embed, "dims": 2, "fields": ["text"]})
ns = ("observatory", "team-cedar", "rules")
store.put(ns, "filter", {"text": "Halpha 教学滤镜说明", "revision": "r1"})
store.put(ns, "timing", {"text": "逐帧读出开销", "revision": "r1"})
hits = store.search(ns, query="Halpha", limit=1)
assert hits[0].key == "filter"

真实 embedding 需与 dims 一致，字段选择决定嵌入哪些内容。单项可设置索引字段或 index=False，避免把无需语义召回的值加入索引。相似度只是召回信号，不能证明某条规则仍有效；结果还需核对 namespace、版本和批准状态。

选择边界#

申请助手要回答的问题 应查询的位置 为什么
A 正等谁审阅哪个草稿 A 的 checkpoint 执行位置属于实例
B 是否可用组内默认语言 可信组 namespace 的 store 数据跨申请共享
A 的工具参数是什么 A 的状态或审计记录 需要追踪特定执行
某条规则何时失效 版本化业务资料与 store 索引 不能只依赖历史对话
进程重启后还能否继续 A 持久 saver 与兼容图版本 内存内容不足以恢复

Store 是外部读写依赖，不与每一步 checkpoint 自动形成统一事务。若节点先写偏好再失败，恢复可能再次写入，需要稳定键与更新规则，不能把每次重试都当成一条新记忆。

用换会话和换进程区分两种保存#

在进程内，A 的状态保存默认中文，B 不会因此自动获得它；写到组 namespace 并让 B 主动读取后，才实现跨 thread 共享。反过来，即使 B 读到中文偏好，也不知道 A 暂停在 v2 的审批处。

退出进程后，内存 saver 和 store 都消失。验证持久性需要启动一个新进程，通过相同地址重新读取；同一对象第二次调用成功只证明当前进程内的连续性。测试记录应明确这两个条件，避免把内存演示写成灾后恢复证明。

一次审批请求的两条时间线#

用一份申请和一条偏好记录分别列出事件：

时点 thread proposal-SIM-OBS-17 组偏好 store
开始研究 保存问题和参数 读取默认语言及其版本
生成 v1 保存资料与草稿 不因生成而自动更新
等待审批 checkpoint 留下待恢复任务 其他申请仍可独立查询
收到拒绝 同一 thread 写入意见，生成 v2 只有明确业务请求才改偏好
批准后 生成本地回执 不保存 Python 执行位置

恢复时节点可能重入，审批前读取外部偏好也可能再次发生。若重新读取会改变预览，就需要将研究时采用的版本固定在 state。checkpoint 不会冻结外部世界，store 更新也不会自动使旧批准失效，这些关系需要业务合同定义。

InMemory 只适合开发#

InMemorySaver 和 InMemoryStore 易于构造和清空，适合隔离测试；进程退出即丢失，也不解决多实例共享。示例选择它们是为了让控制流测试不依赖数据库。

切换到持久实现时，要检查连接初始化、迁移方式、索引与序列化、租户隔离和保留政策。还应定义同一 thread 的并发写入策略，避免两个恢复请求同时推进同一待审版本。数据库能保存数据，不等于业务可以无条件并行恢复。

备份需要覆盖 checkpoint、store 与必要外部对象引用；恢复演练要在新进程验证。包含敏感资料的字段应有加密和访问控制，不能因为只有内部图读取就忽略保存责任。

状态为什么会无限增长#

每轮完整资料、模型消息和重试记录都追加到 state，会使后续 checkpoint 反复携带更大的累计值。某个节点若返回旧列表加新增项，再经追加 reducer 合并，增长还会被重复放大。

先检查记录是否重复和是否真的需要恢复。原始图像、整份手册与长堆栈通常适合放外部存储，state 留版本化引用；模型只需要摘要时，也不必反复发送原文。随后再决定近期窗口、摘要和 checkpoint 保留范围，最后才评估增量存储优化。

压缩状态之前先确定恢复还需要什么#

审批等待期间，草稿引用的资料 r1 不能在清理后只剩一个会变化的 URL。可保留来源、revision 和指纹，或在受控存储中留原始版本。否则批准后无法解释当时依据，也无法准确复现计算。

清理当前 state 不一定删除历史 checkpoint，工具闭环和待审批预览也不能随意裁掉。应分别设计模型上下文压缩、当前恢复状态清理和历史数据删除。它们有不同风险，不能用一个“保留最近两条”同时解决。

短期记忆管理：裁剪、删除与摘要#

上下文窗口有限，短期记忆需要按用途压缩。裁剪通常作用于本次模型输入，删除修改消息状态，摘要则建立一个新的信息表示。三者的持久影响不同，必须说明到底改了哪里。

裁剪（trim）#

下面为模型调用前的消息准备片段：

from langchain_core.messages.utils import trim_messages, count_tokens_approximately

visible = trim_messages(
    state["messages"],
    token_counter=count_tokens_approximately,
    max_tokens=800,
    strategy="last",
    start_on="human",
    end_on=("human", "tool"),
)

visible 是本次输入视图，并没有自动删除 state 中的原消息。近似 token 计数适合预算预检，不是 provider 精确计费；还需检查近期工具请求与观察是否完整，以及保留系统规则的策略是否满足应用要求。

删除（RemoveMessage）#

若要修改当前消息状态，可以返回删除标记。以下为使用 add_messages 的节点片段：

from langchain_core.messages import RemoveMessage

def remove_obsolete_summary(state):
    targets = [m.id for m in state["messages"] if m.id == "obsolete-budget-summary"]
    return {"messages": [RemoveMessage(id=message_id) for message_id in targets]}

删除按消息身份工作，需要相应 reducer 支持。不要只按列表下标删旧消息而破坏工具轮次。当前删除也不会擦除已有历史检查点，涉及隐私删除请求时，必须继续清理保存层和日志中的副本。

摘要（summarize）#

摘要可以保存“当前采用规则 r1，6 帧预算 1500 秒，目标高度未核验”，再缩小较早原始消息窗口。应区分已确认事实、临时方案和否定意见，避免把“未验证可见”压成“可见”。

langmem 提供 SummarizationNode、RunningSummary 等相关封装；也可自己增加 summary 字段并定义更新。无论哪种方式，都要保存来源与未决项，检查摘要错误如何纠正。摘要改变上下文，若同时删除旧消息也改变恢复状态，但不会改变 checkpointer 的职责或自动清除旧历史。

time travel 不是修改过去#

从某个历史 checkpoint 继续，可以重新研究 8 帧方案并产生新分支。旧的本地回执或真实外部占用并不会因此消失，外部世界不跟随图历史回滚。

调试时应把重放分支与真实提交环境隔离，或者让副作用服务按业务身份防重。比较两条分支可以解释不同参数如何导致 1500 与 1900 秒，却不能把其中一条从图里删去就认为真实资源已释放。

一个实用命名策略#

让地址可以解释业务，又不将敏感内容直接暴露其中。thread 表示一份工作流实例，checkpoint ID 定位该实例历史点；namespace 从可信组织和领域构造，key 用稳定业务名而非整句问题。

申请重新开启时，是继续原流程还是创建新实例，应有明确规则。草稿 revision 也不要混同于 checkpoint ID：前者是领域版本，后者是运行存储定位，一份草稿可能跨越多个检查点。

一个地址正确，还不代表访问被授权#

知道 proposal-SIM-OBS-17 的人不应自动有权读取或恢复它。服务端需要核对组织、申请归属、可执行动作与当前批准版本，再使用内部地址访问图。

删除组数据时，要覆盖相关 threads、store namespace、资料对象和观测记录。删除当前一项 key 不代表整个用户历史已清空。若业务允许保留脱敏审计，应明确保留字段和期限，避免删除功能只改变界面显示。

源码入口#

  • langgraph/checkpoint/base/__init__.py：查看 saver 合同、元数据和地址结构。
  • langgraph/checkpoint/memory/__init__.py：核对内存实现保存范围。
  • langgraph/store/base/__init__.py：检查 namespace、item 和搜索接口。
  • langgraph/store/memory/__init__.py：理解索引配置与过滤行为。
  • langgraph/pregel/_checkpoint.py：连接运行时保存内容与恢复机制。

先区分“我在查哪个实例”与“我在读哪条业务数据”，再沿对应接口查找，能避免在错误存储里寻找审批或偏好。

中断、重放与人工审批

值班员明天才有空审阅申请，服务不应为此一直保留一个 HTTP 请求和 Python 线程。interrupt() 让图交出待决定的信息，保存可恢复状态，本轮调用返回；之后另一轮调用带着决定找到同一个流程。

这种暂停适合等待，不等于已经批准，也不保证外部条件保持不变。恢复时要检查草稿版本、身份和资源状态，才能把人的决定用到正确对象上。

基本流程#

以下为已配置持久化的状态图中的节点片段：

from langgraph.types import Command, interrupt

def review(state):
    decision = interrupt({
        "kind": "observatory.review",
        "proposal_id": state["proposal_id"],
        "revision": state["revision"],
        "draft": state["draft"],
    })
    if type(decision.get("approved")) is not bool:
        raise ValueError("approval must be boolean")
    if decision.get("revision") != state["revision"]:
        raise ValueError("stale draft decision")
    return {"approved": decision["approved"]}

首次到达中断时，返回结果中的暂停信息交给应用展示。收到审核决定后，用原配置调用 graph.invoke(Command(resume={"approved": True, "revision": 1}), config)。这份值成为重放过程中 interrupt() 的返回值。完整示例还会检查决定是字典、revision 为整数，以及拒绝后的调度。

最关键的规则：节点可能从头重放#

恢复不是原调用栈在某一行醒来。运行时重新进入节点，利用保存信息和恢复值推进，所以 interrupt() 之前的普通代码可能再次执行。

把“预留真实时段”写在中断之前会有风险。首次调用已经预留，恢复再次进入又预留一次。可以把研究和预览准备留在可重放步骤，将外部提交放在审批通过后的单独节点，并在领域服务中使用稳定业务键。

下面是阶段划分的伪代码，不代表框架自带排班 API：

def approval_node(state):
    return {"decision": interrupt(preview_of(state))}

def reservation_node(state):
    # 应用服务再次检查批准版本，并按业务键返回已有或新建的回执。
    receipt = scheduling_service.reserve_once(state["proposal_id"], state["revision"])
    return {"reservation_id": receipt.id}

即使移到中断之后，提交节点也可能因故障重试。阶段拆分让风险可见，幂等才处理外部重复生效。

两次请求之间没有一条永远挂起的调用栈#

调用 A 到达待审点后可以结束，应用只需把申请地址和审批预览关联起来。第二天调用 B 使用同一 thread 和恢复值继续流程，不要求同一个 Web 进程存活。

因此审批前生成随机编号、读当前时间或刷新草稿都要审慎。重放时这些值若变化，UI 上批准的内容可能与实际处理不一致。先把稳定预览写入 state，再在审批节点只读并中断，通常更容易固定版本关系。

payload 是 UI 合同#

审批 payload 应让客户端知道展示什么和允许做什么。申请编号、修订号、安全预览、动作集合和必要警告比一句“同意吗”更有用。需要编辑的字段还应有受限 schema，不应让客户端回传整份内部 state。

payload 会经过序列化、保存和网络边界，不能带连接对象、秘密或其他申请记录。UI 显示的草稿与服务端批准校验应使用同一 revision 或内容指纹，避免预览和提交对象错位。

对 approved 应严格检查布尔类型，bool("false") 在 Python 中为真。示例专门测试这种输入，防止看似拒绝的文本值成为批准。客户端校验不能代替服务端校验。

多个并行中断#

规则审核和时间审核可以同时暂停。调用方需识别每个 interrupt 的 ID 和业务对象，收集对应决定；不能只取第一个暂停信息就认为整份申请只有一项待处理。

多个恢复值可按中断身份映射，具体输入形状应核对目标版本。相同问题文本不能作唯一键，两个节点都问“通过吗”时仍是不同任务。恢复后还要核对审批是否过期，不能让延迟到达的决定覆盖更新后的申请。

审批的是哪个版本，也应进入合同#

v1 被拒绝后产生 v2，旧页面上的“批准 v1”不应自动批准新草稿。服务端检查业务版本，图节点也检查当前 state revision，不匹配时拒绝使用决定。

版本校验还需覆盖外部变化。即使草稿内容没变，窗口可能已被取消，提交服务仍要确认当前可用性。保存了 v1 预览仅证明当时的草稿，没有冻结排班系统或授权。

静态断点与动态中断#

interrupt_before=["tools"] 在节点边界暂停，适合调试或整体门控。继续这种静态断点通常用同一配置传 None。它并没有在节点内部留下一个等待返回业务值的 interrupt() 调用。

动态中断有业务 payload，恢复时传 Command(resume=...)。需要解释批准对象、动作和版本时，动态方式更合适。两种暂停都依赖保存机制，但客户端恢复协议不能混用。

故障恢复与中断的共同基础#

故障和人工等待都需要找回既有状态与后续工作。前者通常没有合法业务决定，只能按保存结果重试；后者则还需一个外部恢复值。保存地址、图版本和节点边界决定能否继续。

使用内存 saver，进程结束后待审任务随之消失。生产中跨日审批必须选择持久实现并测试新进程恢复，同时考虑等待期间图升级的兼容性。即使 checkpoint 完整，已失效的工具权限也需要重新验证。

一个审批测试应验证什么#

可以从可观察状态编写断言：首次暂停有草稿但无回执，next 指向 review；拒绝后版本增加且仍无回执；批准当前版本才进入本地发布；第三次拒绝结束为额度耗尽；错误布尔值和过期版本不被接受。

examples/test_examples.py 覆盖这些进程内路径以及预算不足、资料缺失的直接结束。它不连接真实数据库或排班服务，不能据此宣称完成了跨进程恢复、并发审批或外部副作用防重测试。

拒绝审批后如何确认没有生成提交回执#

只检查草稿变了不够，还要断言回执为空、发布计数为零，以及审核意见进入了正确版本。若领域服务被替换为可计数测试桩，拒绝前后计数都应不变，批准后才允许一次逻辑提交。

真实服务还应注入“写入成功但响应丢失”，再用同一业务键查询与重试。重复 HTTP 决定在应用层去重，图状态与外部记录共同核对，才能验证没有重复预留。离线例子只有稳定本地回执，不冒充这项保证。

源码入口#

  • langgraph/types.py：核对中断值、恢复命令和中断身份。
  • langgraph/_internal/_scratchpad.py：追踪重放时如何找到已有恢复信息。
  • langgraph/pregel/_loop.py：检查本轮暂停和下一轮恢复的推进。
  • langgraph/checkpoint/：查看保存实现承担的持久性边界。

读中断实现时，要同时查看调用它的节点和 saver 配置；只看一行 interrupt() 无法判断副作用是否可重放。

流式输出不是一种流

资料检索没有模型 token，却仍有进度；草稿开始逐字生成，也不代表预算计算或审批已完成。若页面只订阅一种模糊的“流”，很容易把展示进展和业务终态混在一起。

LangGraph 可输出消息增量、状态更新、完整值或自定义进度。客户端需要选择数据合同，并在公开前做适配。流出得早只影响可见时机，不提升数据的可信度或执行资格。

四类常见需求#

模型消息流#

草稿节点调用支持流式的模型时，可以让用户逐步看到文字。消息 chunk 可能含工具参数片段和元数据，不能假定每项都可以当字符串追加。

页面可只显示允许的文本块，工具准备状态单独呈现。最终仍需把合并结果与节点写入的草稿核对，避免增量遗漏或重复。

状态更新流#

updates 表示节点产出的局部变化，适合展示资料已找到、预算已算出等事件。比如 total_s 从未设置变为 1500，是一项状态变化，不是模型说出“1500”这个 token。

这类事件也可能包含内部字段，应提取允许部分。不要因为增量比全量小，就假定它天然不敏感。

状态快照流#

values 提供步骤后的状态视图，适合受控调试和状态面板。累计资料和内部计划都可能出现，传输量也随状态增长。

快照应替换客户端当前视图，不应被当成新增文字。若每次把全量草稿追加到聊天框，最终会看到多份重复草稿。

自定义进度流#

资料扫描可以报告“核验了 2/5 个来源”。这种瞬时进度不必全部保存到 state，也不应伪装成模型结论。

进度可以合并或限频，最终确认结果则应从状态或持久记录读取。收到 100% 只说明工具完成某项扫描，不表示审批或外部提交完成。

同一轮运行，可以有两种不同的时间线#

时间点 用户展示通道 业务状态通道
查询开始 正在检查两条教学规则 尚无新资料更新
查询完成 显示来源编号 notes 写入两条记录
生成中 可选的草稿文字增量 当前 draft 未必已完整写入
审批暂停 展示 v1 预览和动作 待恢复任务为 review
本地发布 展示模拟回执 状态为 published_locally

这张表拆开体验与确认时点。具体事件先后仍受实现和配置影响，不是对数据库提交顺序的统一保证。客户端应按事件类型处理，不能从任意文字推断完成。

stream mode 是数据合同#

下面为已构造 graph 后的调用片段：

for update in graph.stream(
    {"question": "研究 Halpha 申请", "notes": []},
    config,
    stream_mode="updates",
):
    print(update)

它适合本地观察节点增量。异步服务使用异步消费，避免在事件循环里同步等待。另一些较新的官方文档提供 stream_events(..., version="v3") 统一事件表面，需先确认已安装版本的签名，不把它和其他版本的事件对象混用。

对外可以定义自己的协议，比如 {"type":"proposal.progress","run_id":"r17","sequence":4,"data":{"completed":2}}。run 身份隔离执行，递增序号辅助去重，data 只包含允许字段。框架升级改变内部事件时，适配层继续维持客户端合同。

工具调用参数不能边到边执行#

预算参数 {"frames":6,"exposure_s":180} 可能分几次抵达。工具名出现时只能显示准备调用，参数完整后还要进行范围和权限校验，才可以执行。

即使某个前缀暂时是合法 JSON，也不能认为它代表最终请求。完成信号、调用 ID、完整参数和授权共同决定可执行性。自定义 provider 转发器如果绕过框架合并逻辑，需要自行维护这一合同并补测试。

背压与取消#

生产者产生事件比浏览器读取更快时，服务端队列会积累。应为队列设上限，对可替代进度合并，对不可丢失文字定义断开与重放策略，避免无限内存增长。

取消也分阶段。客户端关闭页面，后台 run 可以继续保存结果；如果希望停止，需要向模型与工具传播取消信号。已经发生的真实资源预留不能靠取消本地迭代器自动撤销，必须查询外部状态或走业务取消流程。

消费慢与停止运行是两个问题#

慢消费者只是来不及接收，不代表用户放弃申请。可减少进度频率，但不能随意丢中间文字后继续追加，否则草稿残缺。必要时让客户端重新读取最新完整草稿，再从新的事件位置继续。

停止运行则应明确：哪些节点可立即中止，哪些写操作必须确认结果，暂停审批是否保持。记录 cancel_requested 和最终业务状态比仅记录连接断开更有用，断线本身没有事务含义。

私有状态也可能被流出#

输入和输出 schema 限定常规接口，不必然筛选所有流模式。values 可能包含内部 channel，调试事件还可能携带工具参数、system prompt 和资料内容。

用户出口应采用白名单映射，而非仅删除几个已知秘密字段。新增内部字段默认不公开，测试中放入醒目的敏感哨兵值，断言所有用户事件都不包含它。日志、trace 和错误响应也要单独检查，因为它们是不同出口。

observability 与用户流分开#

消费者 应得到的信息 通常不应直接得到的信息
申请页面 安全进度、草稿、待审版本、本地回执 内部计划与堆栈
运行诊断 节点时间、工具身份、失败类型、尝试数 无关原始敏感资料
审计记录 批准主体、版本、业务键和状态 不必要的全部模型上下文

可以从同一次运行派生多个适配出口，但分别做脱敏和授权。诊断追求细节，页面追求稳定，审计追求可解释的业务事实，三者不需要共享一个未经筛选的 payload。

测试流式行为#

除最终草稿外，应断言增量合并等于终态、序号递增、工具未在调用完成前执行、暂停能结束本轮消费、私有哨兵值未泄漏。再模拟慢读取和中途断开，确认队列有界且最终状态可查询。

这些测试不全需要真实模型。可用固定 chunk 序列覆盖适配逻辑，再用少量目标 provider 合同测试核对原生事件形状。不能把确定性 LangGraph 示例的成功当成网络 streaming 链路已经验证。

重连时如何避免把同一段文字显示两次#

客户端按 run_id 和 sequence 识别重复事件，服务端定义可重放窗口；窗口失效时返回完整快照与新的游标。快照替换已有草稿，增量才追加，二者在协议中必须有不同类型。

还需避免把旧 run 的尾部增量拼到新一轮草稿。重连后先确认执行身份和草稿 revision，再决定续接或重载。只有内存广播而没有重放记录时，应明确只能查询最终状态，不能假称支持断点续流。

源码入口#

  • langgraph/stream/：查看当前快照的事件类型和转换路径。
  • langgraph/pregel/main.py：核对流式方法、mode 和版本参数。
  • langchain_core/language_models/chat_model_stream.py：追模型 chunk 的标准化。
  • langchain_core/runnables/schema.py：对照事件结构，避免与公网协议耦合。

排查时把“产生了什么”“适配后剩什么”“客户端如何消费”分别记录，才能定位缓冲、重复或泄露发生在哪一段。

子图与多 Agent：先隔离上下文

观测研究可能同时涉及仪器规则和历史资料。把它们拆成两个专家之前，应先决定每个专家允许看到什么、返回什么，以及失败怎样影响申请。增加角色名称不会自动产生知识或可靠性，清楚的数据边界才使拆分有价值。

子图提供一个可独立定义状态和完成条件的单元。它可以包含模型，也可以完全由确定性节点组成；多 Agent 只是使用子图的一类方式。

先问为什么要拆#

若历史资料检索需要独立权限、上下文很长，且结果能用窄对象返回，就值得考虑子图。它可以单独测试和升级，也能把主流程不需要的工具尝试留在内部。

如果只是同一份两条规则分别加上“仪器专家”和“研究专家”的 prompt，收益可能很小，却多出模型调用、路由和预算管理。先用一个 Agent 配合确定性预算工具，遇到可复现的上下文或权限问题再拆，比较拆分前后的轨迹质量与成本。

子图的两种数据边界#

共享 state key#

父子图拥有同名且含义相同的字段时，可把编译子图直接作为节点。比如二者都使用 question 和 findings，子图读问题、回传核验结果，父图继续审批。

共享意味着更紧的合同：reducer、字段版本和可见范围必须一致。两个子图都写 messages 时，要确认它们是否真的属于同一消息历史，而不是为了少写映射把不同专家对话混到一起。持久化还需理解父子 namespace 和 checkpointer 配置。

显式输入输出转换#

不同状态或权限范围时，父节点选择输入，调用子图，再映射允许结果。以下为已构造 instrument_graph 的包装片段：

def inspect_instrument(state):
    child_input = {
        "filter_name": state["filter_name"],
        "allowed_rules": state["allowed_rule_ids"],
    }
    checked = instrument_graph.invoke(child_input)
    return {"instrument_finding": checked["public_finding"]}

子图无法因为父状态含申请人私人信息就自动读到它，输出也只通过明确字段进入父图。真实接入还要正确传播配置和运行上下文，特别是涉及暂停和恢复时，不能把独立 invoke 当成无条件共享父保存地址。

专家不需要看到主流程的全部历史#

仪器子图需要滤镜名称和允许查询的规则，不需要审批人账号、通知地址或真实提交工具。窄输入降低误用和泄露范围，也让固定测试更容易构造。

输出则应包含直接观察、来源版本和未决项，不要返回完整工具日志让父模型再猜重点。若父图需要审计中间过程，可以在受控观测系统中保留子轨迹，不必把它们全部变成主上下文。

常见多 Agent 模式#

路由（Router）#

路由选择仪器、归档或澄清路径，适合问题类型较互斥的入口。输出可约束为枚举，并保留 unknown，避免把不支持的天体动力学问题硬塞进仪器专家。

路由错了时，应允许返回不适用结果再升级，而不是无限转发。测路由要覆盖混合问题与陌生领域，不只测试关键词明显的例子。

子 Agent（Subagents）#

主助手把“核对 SIM-FILTER-2@r1 的限制”交给窄子任务，完成后收集结果。主流程保留控制权，子任务不直接批准申请。

委托应有完成 schema、预算与允许工具。主助手只看到最终摘要不等于失败不存在，返回值需要明确成功、缺证据或依赖故障。

交接（Handoff）#

当研究结束进入值班审核时，可以正式转移当前处理角色和允许动作。应用需保存接收方、必要上下文与转移原因，确保下一轮交互由正确处理者接管。

一句“请找值班员”只是文本建议，不构成控制转移。真正 handoff 会改变路由和状态，并定义无人接手、超时或拒绝接手时如何处理。

自定义流程（Custom workflow）#

固定预算、两个研究子图、人工审批和本地发布可以混合在同一图中。模型只在需要解释或研究时参与，确定性规则直接由代码执行。

这种组合让关键约束更容易测试：任一必需核验缺失就不进入批准路径，拒绝只修订当前版本，预算耗尽有单独终态，不需要所有动作都由专家聊天决定。

Context engineering 比角色描述重要#

角色提示可以说明研究侧重点，但质量更依赖实际输入：允许来源是否完整，单位是否明确，已确认事实是否与用户猜测分开，缺资料时能否返回未知。工具集合与完成 schema 同样影响专家能做什么。

对比两种上下文可看出差异。只写“你是精密仪器专家”仍可能让模型猜读出时间；直接给出 SIM-TIME-4@r1 的 20 秒与 300 秒，并要求只使用已引用开销，才有可核验的计算依据。

多个角色的多数意见不是独立证据#

三个专家都引用同一条错误规则，只产生一个共同错误来源，不是三份独立支持。聚合应按资料身份与版本检查依赖，记录分歧来自规则、计算还是推断。

比如两个专家说余量 300 秒，一个说 400 秒，应重算 6 × 200 + 300，而不是投票。确定性计算可以直接裁决算术，资料是否适用则要回到原规则与使用范围。

记忆放在哪一层#

子图内部临时查询和工具观察留在其 state，父流程所需结论映射回父 state，跨调用继续靠 checkpointer，跨申请共享的已确认偏好用 store。每份数据只在需要的范围复制。

若子图应每次独立研究，不要无意复用持久子会话；若需要多次交互积累，则明确其保存配置与身份。父 thread、子 namespace 和业务申请号是不同标识，应分别命名和测试。

并行专家与聚合#

规则和归档查询互不依赖时可以并行。聚合结果应包含每项任务的身份和状态，让父图判断哪些已完成、哪些仍缺失。一个教学证据对象可写为：

finding = {
    "task_id": "filter-check",
    "claim": "Halpha 方案仍需真实仪器配置核验",
    "source": "SIM-FILTER-2",
    "revision": "r1",
    "basis": "fixture_observation",
    "status": "complete",
}

basis 区分教学记录、源码事实或模型推断，不把一个置信分数当成来源。真实系统应使用自己的枚举与 schema 校验，并在聚合时按任务 ID 排序去重，而非简单拼接长篇专家发言。

失败隔离#

父图应定义子图超时、暂停和失败分别如何呈现。部分成功是否可继续，取决于结论需要哪些证据；仪器安全核验缺失时，不能为了出报告跳过。

重试额度也要分层。两个子任务各最多尝试两次，父图再整体重跑三次，最坏可能出现十二次依赖调用。明确总预算，并优先重试失败的窄任务，避免成功结果和费用被重复放大。

部分成功应成为明确的聚合状态#

可保存 filter-check=complete、archive-check=timeout，然后给出“规则已核验，归档证据尚缺”的结果。它不同于整体失败，也不同于全部通过。

等待重试期间，已完成结果可能过期。聚合前检查来源版本和时效；若失效，则说明为何重新核验。隔离失败不等于隐藏失败，父层必须收到足够信息来作决定。

源码入口#

  • langgraph/graph/state.py：查看编译子图作为节点的连接方式。
  • langgraph/pregel/main.py：核对子图状态、保存和流式处理。
  • langchain/agents/factory.py：检查可嵌入的编译 Agent 图。
  • 官方 Subgraphs 与 Multi-agent 页面：对照共享状态、显式映射及协作模式的公开合同。

可先构造一个不含模型的仪器子图，验证输入隔离和结果映射，再决定是否需要独立专家循环。

完整案例：观测申请的证据与审批

本章将天文台观测申请组织成一个可运行的研究与审批流程。它读取两条教学资料，计算预算，生成待审草稿，拒绝后修订，批准后生成本地回执。模型行为全部由确定性代码代替，LangGraph 的状态、检查点和中断则是真实 API。

完整入口仍为 examples/research_assistant.py，离线测试在 examples/test_examples.py。示例不占用真实望远镜资源，也不根据天文坐标判断可见性。

需求#

默认输入研究 Halpha 申请，采用 6 帧、每帧 180 秒、1800 秒窗口。教学规则 SIM-TIME-4@r1 给出读出 20 秒和校准 300 秒，结果为 1500 秒。另一个来源 SIM-FILTER-2@r1 记录需要核对真实滤镜配置。

图要区分四种结束：获批后本地发布、无资料、预算超限、三版均被拒绝。审批前回执必须为空，拒绝修订不得重复检索材料。状态的关键部分如下，其余可选字段见完整文件：

from operator import add
from typing import Annotated, TypedDict

class Finding(TypedDict):
    source: str
    revision: str
    text: str

class ResearchState(TypedDict, total=False):
    question: str
    proposal_id: str
    notes: Annotated[list[Finding], add]
    draft: str
    total_s: int
    revision: int
    approved: bool
    receipt: str
    status: str

total=False 允许最初只提供少数字段，并不自动补默认值。plan() 校验参数后写入默认值，后续节点才能读取。notes 累计新增资料，当前草稿与修订号则覆盖更新。

图形#

用状态转换表列出每条有业务含义的出口：

当前节点 条件或结果 后继
plan 参数校验完成并选择研究项 search
search 返回版本化资料记录 draft
draft 有证据且 1500 不超过 1800 review
draft 无证据或预算超限 cancel，再结束
review 严格布尔批准，版本匹配 publish，再结束
review 拒绝且 revision 小于 3 revise，再回 review
review 第三版仍被拒绝 cancel，再结束

review 使用 Command，因此没有通往 publish 的无条件固定边。若误加这条边，拒绝也可能调度发布，测试必须检查这项负面行为。

为什么计划和检索分开#

计划节点选择 filter 与 timing 两个研究项，检索节点只按这些项读取 fixture。尽管代码很短，它们代表不同合同：计划决定研究范围，检索提供实际观察。换成模型或远程资料库后，两者会有不同的错误与重试政策。

本例只在问题包含 Halpha 时生成研究项，未知问题得到空计划，不使用万能默认资料。这样无命中分支可直接验证，也不会把与问题无关的内容包装成研究成功。

沿一份草稿跟踪状态怎样变化#

输入只有 question 和空 notes。plan 写默认申请号、帧数、曝光、窗口、revision=1 和空回执；search 新增两条资料；draft 写 total_s=1500、草稿与 awaiting_review。

审阅节点首次中断，尚未写 approved=True。拒绝 v1 后，意见写入状态，revise 把 revision 变为 2，并在草稿中增加具体意见和待核验条件，notes 仍为两条。批准 v2 后，publish 生成 local:SIM-OBS-17:v2。这是稳定的本地结果标识，不是数据库幂等实现或远程申请确认。

首次运行#

下面可在项目根目录和已安装 LangGraph 的解释器中运行：

from examples.research_assistant import build_graph

graph = build_graph()
config = {"configurable": {"thread_id": "proposal-walkthrough"}}
paused = graph.invoke({"question": "研究 Halpha 申请", "notes": []}, config)
assert paused["total_s"] == 1500
assert paused["receipt"] == ""
assert paused["__interrupt__"]
assert graph.get_state(config).next == ("review",)

next 表示待恢复工作，不能据此断言 review 从未执行。它已经到达中断位置，恢复会重入节点。计算与草稿放在前序节点，有助于保持审批预览稳定。

恢复审批#

沿用前面的 graph 和 config，先拒绝再批准：

from langgraph.types import Command

revised = graph.invoke(Command(resume={
    "approved": False, "revision": 1,
    "feedback": "说明未核验真实目标高度。",
}), config)
assert revised["revision"] == 2
assert revised["receipt"] == ""
finished = graph.invoke(Command(resume={"approved": True, "revision": 2}), config)
assert finished["receipt"] == "local:SIM-OBS-17:v2"
assert graph.get_state(config).next == ()

申请地址不能更换，revision 必须对应当前草稿。示例还拒绝 approved="false" 这种字符串，防止 Python 真值转换误判。完整授权不在例子内，真实 API 应先验证审阅者资格，再调用图。

拒绝并不意味着从头重跑#

普通文字修订只需处理当前草稿和意见，已确认规则不必再查。示例返回 review 时，检索计划和两条 notes 保持不变，测试断言材料数量仍为 2。

如果意见指出规则错误，真实产品应增加重新研究分支，而非仅附加说明。图的合同应区分“表达修改”和“证据失效”；本例只演示前者，修订不意味着已经修正任何真实观测可行性问题。

替换成真实模型#

可以先替换 draft，保持它只返回 draft 等约定字段。以下是应用接口伪代码，不是可直接运行的 provider 示例：

def model_draft(state):
    request = compose_research_request(
        question=state["question"], findings=state["notes"],
        computed_total_s=state["total_s"],
    )
    response = configured_model.invoke(request)
    return {"draft": extract_text(response)}

数值预算继续由确定性代码计算，不让模型随意改公式；模型补充解释和未核验项。接入后做输出 schema、引用完整性和 provider 合同测试，不能只检查文字流畅。

替换成真实检索#

真实资料结果至少包含稳定来源、revision 和文本，必要时再有 URI、内容指纹和召回分数。图应保留足以复核审批依据的字段，不能只返回“找到了相关文档”。

召回分数用于排序，不等于规则真实或适用。检索服务要按可信组身份授权，明确空结果、权限拒绝与超时；原文过大时保留受控外部引用，并固定版本，避免审批等待期间 URI 指向另一份内容。

从内存切到生产存储#

当前 build_graph() 每次创建新 InMemorySaver，因此新对象看不到旧实例，进程退出也无法恢复。切换持久 saver 需要调整构造与连接生命周期，而不只是更换一个导入名。

应测试初始化和迁移、连接池、序列化、同 thread 并发策略、数据保留以及旧图版本恢复。真实发布还需要独立业务记录和幂等服务，本地 receipt 字段不能代替跨系统事务。

接上真实依赖后，先保持图的合同不变#

一次只替换一个边界：模型仍产出受限草稿，检索仍返回版本化 findings，审批仍提交严格布尔值和 revision。保留原离线回归，有助于区分控制流回退和外部能力差异。

持久性验证必须跨进程：进程 A 跑到 review 后退出，进程 B 用同一保存地址和兼容图继续。外部提交则注入响应丢失，确认重试读取原回执。完成这些之前，只能说接入了依赖，不能说恢复和副作用已可靠。

测试分层#

节点测试#

直接检查 plan 的默认值与拒绝输入，search 的来源记录，draft 的 1500 秒计算，以及 publish 在未批准时抛错。这些断言固定领域含义，不需要驱动整张图。

图测试#

使用内存 saver 检查首次暂停、拒绝后 v2、批准后结束、thread 隔离、三次拒绝上限、无资料和超预算直接退出。错误批准值与过期 revision 必须不产生回执。

集成测试#

接真实资料库、模型和持久 saver 后，分别核对权限、消息协议、序列化与进程恢复。真实模型测试应限制请求和费用，并评估来源与未决项，不能用它替代确定性路由回归。

运行#

在具备 LangGraph 依赖的环境中保留原 CLI，并运行新增测试入口：

python examples/research_assistant.py
python examples/test_examples.py

第一个命令演示拒绝 v1 后批准 v2，打印草稿和本地回执；第二个使用标准库 unittest 运行离线断言。若使用项目虚拟环境，可将 python 改为 .venv/bin/python。安装依赖不属于离线测试本身，准备好环境后，这两个入口不访问远程模型或天文台服务。

生产检查表与源码阅读路线

离线申请能走到本地回执，只说明特定输入下控制流成立。真实系统还要面对排班变化、请求重复、进程退出和旧任务恢复。上线判断应有失败输入与可重复验证，不能由一次顺利演示代替。

本章把这些验证绑定到观测申请对象，再给出追踪源码的方法。逐项填写失败输入、预期结果和已有测试，空白处就是还缺的证据。

上线前检查表#

状态#

为 total_s 固定单位和公式版本，为 notes 固定来源身份与去重规则，为 draft 和 revision 固定覆盖关系。并行节点的写入集合应可列出，冲突字段有明确聚合节点或 reducer。

检查最大规模和出口：整幅观测图像不应反复进入 checkpoint；模型输入窗口与恢复状态分别管理；用户事件只输出白名单字段。测试中放入敏感哨兵值，确认它没有出现在不允许的出口。

控制流#

明确无资料、超预算、拒绝耗尽和正常完成四类状态，不能只检查图是否结束。循环记录剩余额度或版本，取消和超时也有可解释结果。

并行核验需要哪些结果、是否允许降级，应在聚合规则中写明。空输入集合、某支路超时和延迟决定都要测试，避免正常路径图像掩盖缺失依赖。

工具与副作用#

每个入口校验单位、范围和身份，敏感写操作核验当前批准版本。模型可见工具列表只是前置限制，领域服务仍做最终授权。

真实窗口预留和通知使用稳定业务键，记录参数指纹与外部回执。超时先查结果，不把未知状态改成未执行。对同一键不同参数的请求，服务应明确拒绝冲突，不能静默返回无关旧结果。

持久化#

用可信申请映射 thread，防止跨组恢复。检查 saver 初始化、迁移、备份和保留策略，store namespace 由服务端身份构造。

跨进程恢复要实际执行，旧 checkpoint 要在新图中验证语义。同一实例并发调用如何串行化或拒绝也需定义，不能依赖 UI 按钮只点一次。

观测与评估#

运行记录关联申请、run、图版本、资料版本和必要模型配置。指标分开统计研究耗时、外部等待、尝试次数与人工等待，避免把一天审批误判成模型延迟。

答案评估检查引用、算术和未知项，轨迹评估检查权限、调用次数及预算。失败样本脱敏后进入回归，trace 本身也应控制访问和保留范围。

把检查表还原成一次真实故障#

假设远程排班已预留窗口，应用保存回执前崩溃。恢复从旧状态重试提交，若业务键不稳定，就会重复占用；若 thread 归属未校验，另一个课题组还可能触发这次恢复。持久化、幂等和授权必须沿同一条链检查。

再看答案正确但轨迹错误的情况：最终 1500 秒计算无误，却读了未授权资料并发出十次重复查询。仅按答案评分会放过问题，轨迹需要记录资料身份、工具次数和拒绝信息，而不是为了排障直接保存全部私密内容。

四类测试#

1. 确定性节点测试#

用固定参数直接检查预算、资料映射和修订更新。6 帧得到 1500 秒，8 帧得到 1900 秒；负帧数、错误单位或未批准发布应被拒绝。失败时能直接定位函数，而不必解析整条 Agent 对话。

2. 图结构与路由测试#

用固定节点或 fake model 驱动整图，断言待恢复节点、资料数量、版本变化和终态。刻意覆盖拒绝不发布、第三版停止、并行字段冲突等负面路径。

当前 examples/test_examples.py 提供这一层的部分回归。它使用内存保存，不测试跨进程，也不证明所有并行模式；后续增加新控制路径时，应增加对应最小断言。

3. Provider 合同测试#

针对计划使用的 provider，少量验证工具 schema、消息闭环、结构化结果和 chunk 合并。用受限请求和费用预算运行，记录目标模型及适配包版本。

本地 fake 无法证明真实服务接受某种消息排列；真实服务一次成功也不能覆盖所有图分支。两层测试各有用途，不应互相替代。

4. 轨迹评估#

检查实际查询是否都在白名单来源内、预算工具是否使用正确参数、是否无故重复调用、最终草稿是否遗漏未核验事项。对相同答案，合理轨迹与危险轨迹应得出不同评估结果。

可建立失败样例：不可信资料要求绕过审批、超预算方案被模型美化、过期版本请求继续发布。评估关注能观察到的行动，而不只是措辞是否谨慎。

升级策略#

升级前记录依赖、图 schema 与资料合同版本，读目标变更，再运行确定性回归和少量 provider 合同测试。新 thread 能正常生成后，还要恢复旧暂停实例，比较批准、拒绝和取消分支。

采用分批发布时，观察错误率、图步数、工具尝试数、费用和恢复失败，不只比较总延迟。若涉及 channel 或 checkpoint 格式，回滚方案要包含旧实例如何继续，不能仅退回代码包。

DeltaChannel 等 beta 能力有额外格式约束。旧运行时不能理解新存储时，应隔离受影响 thread、迁移或让兼容版本跑完，而不是强行加载后假定结果正确。

升级测试为什么必须带一份旧 checkpoint#

旧状态可能保存 review 节点和秒为单位的窗口，新版若改节点名或把窗口解释成分钟，反序列化成功也会误判。用脱敏旧副本恢复，核对待审 revision、1500 秒预算与后续回执身份。

测试副本不能连接真实提交服务，避免把升级验证变成第二次预留。需要外部合同测试时，用隔离环境和独立业务身份，并明确哪些结果来自模拟、哪些来自真实服务。

源码阅读路线#

想看 Agent 工厂#

先在 langchain/agents/factory.py 找返回类型、模型节点、工具节点和条件路由；再查看 middleware/types.py 中 hook 合同、structured_output.py 的策略，最后进入 langgraph/prebuilt/tool_node.py 和 graph/state.py。

带着“哪项配置增加了哪个节点”比较几个最小构建，比先读完所有重载和兼容分支更有效。工具未注册与模型未选择要在这里分开诊断。

想看状态合并#

从 graph/state.py 中字段注解到 channel 的转换开始，查看 channels/last_value.py、channels/binop.py，再到 pregel/_algo.py 的 apply_writes。

记录旧值、两份节点更新和最终值，特别检查节点是否误返回整段旧列表。用一个来源 ID 的重复输入即可构造最小反例，不需要启动真实模型。

想看恢复与中断#

在 types.py 找 interrupt，通过 _internal/_scratchpad.py 查看恢复信息，再追 pregel/_loop.py、pregel/_checkpoint.py 及 saver 接口。

同时列出中断前的所有副作用和非确定性读取。运行时能解释节点如何重入，领域服务才能解释再次调用为何不会重复预留，两条路径要一起看。

想看流式#

先核对 pregel/main.py 的公开方法与 mode，再进入 stream/run_stream.py、stream/_types.py 和相关转换器。不同版本的事件对象要按对应签名解读。

从一个 chunk 或 update 一路追到公网适配器，记录它何时被筛选、序号怎样分配。模型已产出而页面不动时，这条路径能定位缓冲发生在哪一段。

避免低效阅读#

不要按目录顺序把兼容代码都读一遍。先确定目标版本和失败对象，用符号检索找到生产者与消费者，再看测试是否已有相同边界输入。

公开 docstring 描述用法承诺，实现体现当前分支，测试帮助理解限制；三者不同就先核对版本和调用路径。带 deprecated 标记的历史入口不应自动成为新代码设计依据，平台宣传也不能替代恢复与事务语义。

一次排查应该跟着对象走#

预算错了，追参数、公式与单位；资料重复，追节点返回值和 reducer；恢复批准错位，追 thread、revision 和恢复值；用户数据泄露，追 state 到事件适配器。

修复后保留最小失败输入与预期终态。比如 approved="false" 不应通过，v1 决定不应批准 v2。这样的回归比一句“加强校验”更能防止升级时重复同类错误。

最终心智模型#

要定位的对象 主要层级 首个检查点
模型请求与工具观察 LangChain 协议与 harness 名称、schema、调用 ID
草稿版本与后续节点 LangGraph 状态转换 partial update、路由、批准合同
同步步骤与并发合并 Pregel 触发、channel、写入与保存
真实窗口与通知 应用领域服务 授权、幂等键、外部回执
页面和诊断轨迹 事件适配与观测系统 出口白名单、消费及重连合同

按对象定位后，再选择工具或源码入口。框架能帮助组织执行，申请所依据的事实、权限和外部状态仍需有各自可验证的记录。

Deep Agents：create_agent 之上的 harness

一份较长的观测研究可能需要整理资料文件、维护待办、调用窄专家并压缩历史。只用 create_agent 也能逐项实现，但许多项目会重复搭建同一组外围能力。Deep Agents 将这些能力组合为 harness，入口通常是 create_deep_agent。

它继续利用 LangGraph 的执行机制。新增的是默认工具、策略和上下文组织方式，不是另起一套检查点或中断系统。本章涉及独立 deepagents 包及官方文档，具体签名应按安装版本核对，不能从两个核心仓库的提交推断全部实现。

create_deep_agent 默认装了什么#

官方描述强调 planning、subagents、filesystem 和 context management。可以按观测研究的实际工作理解这些模块：

模块 对申请研究可能有用的能力 必须另行确认的边界
FilesystemMiddleware 读取资料、维护研究附件和检索文件 backend 可读写范围及是否允许执行
SummarizationMiddleware 压缩早期研究交互 摘要是否保留来源和未决项
SkillsMiddleware 按需加载仪器研究流程 技能来源、可信性与加载成本
TodoListMiddleware 记录待核验规则和任务进展 勾选完成不等于证据正确
SubAgentMiddleware 委托窄范围资料核验 子任务权限、预算与失败返回

默认组合会随版本变化，能力也可能受 backend 支持限制。采用前应检查实际暴露的工具列表，尤其是文件删除、命令执行和外网访问；不要因为是官方 harness 就跳过权限审查。

从零搭一遍，看清每块补什么#

原官方教程以数据分析讲逐步组装，这里改用“为 Halpha 申请整理研究附件”的教学设计，不声称已经运行沙箱。先用标准循环只返回资料摘要，再依据真实缺口加能力：

研究遇到的缺口 可增加的模块 接入后的最小检查
资料附件要保存并再次读取 文件 backend 与文件中间件 只访问工作目录，路径越界被拒绝
多轮修订挤掉早期规则 摘要中间件 r1 来源、1500 秒预算和未知项仍在
仪器流程只在少数任务用到 技能中间件 未命中时不载入全文，命中后可找到来源
多个来源各需独立研究 子 Agent 与待办 子任务有窄输入、结束状态和预算

组装关系可用下面的伪代码表达，类名和构造参数应按实际版本选择，不把它作为可直接运行的调用：

research_harness = assemble(
    base_agent=standard_model_tool_loop,
    filesystem=restricted_workspace_backend,
    summarizer=source_preserving_summary,
    skill_sources=[approved_instrument_skills],
    delegates=[filter_rule_reviewer],
)

只有明确需要整套默认组合时再选择 create_deep_agent；若只缺摘要，直接为现有 Agent 配置相应中间件更容易控制变化。每增加一项能力，先验证一个允许案例和一个拒绝或失败案例。

沙箱是边界，不是可有可无#

文件中间件提供操作入口，backend 决定操作实际发生在哪里。内存状态型、宿主文件系统和远程隔离执行环境不是同一种安全边界。LangSmithSandbox 是文档中的一种沙箱选项，不代表所有文件 backend 都自动具备同等隔离。

为观测研究配置沙箱时，明确可挂载的资料、网络出口、命令权限和资源额度。虚拟路径不等于可靠隔离，路径校验、符号链接、宿主挂载和凭据注入都需检查。若服务允许执行命令，能力面远大于几个文件工具。

研究附件也不会自动回到主机或长期保存。任务结束前应选择需要保留的文件，记录来源版本和内容指纹，再经受控接口导出。沙箱销毁与 checkpoint 保留的生命周期不同，恢复时还要处理附件已不存在的情况。

技能用渐进披露省 token#

技能启动阶段通常只暴露名称和描述，需要时才加载完整说明。下面是一份教学技能文本，演示领域流程的组织，不是仪器操作规程：

---
name: observatory-budget-review
description: 为模拟观测申请核对曝光、读出和校准预算
---
读取当前申请参数，保留原始单位。
查找已批准的开销资料及其 revision，再计算总秒数。
报告窗口余量，并列出未包含的真实观测条件。
不执行排班预留，不把计算通过写成人工批准。

技能降低常驻上下文成本，不会消除载入后的 token 开销，也不会自动增加工具权限。技能内容若包含脚本或外部命令，应按来源可信度审查。一个写着“可以读取全部主机目录”的说明，不应改变 backend 授权。

子 Agent 隔离的是上下文#

可以委托子 Agent 核验一批滤镜资料，让它内部进行查询和修正，只向主助手返回来源版本、限制与未决项。主上下文不必承载每轮失败和重试，能减少干扰。

隔离上下文不等于隔离所有权限或进程。子 Agent 可能共享模型、工具 backend 或存储，取决于配置；审计系统也可能保留其完整轨迹。不能绝对声称主流程永远看不到中间细节，应区分模型收到的委托结果与开发者可访问的观测记录。

需要精确控制每个恢复位置、公开输入输出和并行聚合时，显式子图更容易检验。只需把一段窄研究收敛成结果对象时，中间件委托可以减少组装，但仍要处理超时、预算和不完整结果。

什么时候不需要 Deep Agents#

两条教学规则加一个预算计算没有文件工作区、长历史或多专家需求，普通 create_agent 或确定性图就足够。本书端到端例子选择后者，是为了把审批和停止条件写清楚。

若业务顺序严格，不能让 Agent 随意决定何时结算或提交，应在外层状态图固定边界。只用一块通用能力时，单独配置比整套默认 harness 更容易审计。选择依据是实际缺口和测试结果，不是名字中是否带 deep。

源码入口#

  • deepagents 的 create_deep_agent：核对当前版本实际添加了哪些能力。
  • deepagents/middleware/：分别查看文件、摘要、技能、子任务与待办的合同。
  • deepagents/backends/：检查存储路径、执行支持与隔离责任。
  • 官方 deep-agent-from-scratch：用于对照逐步组合方式，不沿用其数据分析案例。

阅读后可列一张“实际工具、backend 权限、状态字段、失败出口”的清单，再决定观测研究需要启用哪几项。没有沙箱实测时，只描述设计与文档合同，不给出隔离或性能已经验证的结论。

多 Agent 与 MCP：协作模式与工具互联

研究助手可能需要仪器专家、归档检索和远程资料服务。前两个是工作怎样分配，后一个是工具怎样连接，它们不应混成同一种架构选择。多 Agent 模式组织控制与上下文，MCP 标准化客户端和工具服务之间的协议。

本章继续使用观测申请，分别检查协作和连接的边界。无论封装多少层，人工批准、最终授权和外部副作用仍需有明确归属。

多 Agent 官方模式#

官方文档介绍 handoff、router、subagents、skills 等模式，也允许混合自定义流程。选择时先描述控制权是否转移、任务是否独立、知识是否只需按需加载，再对应封装。

交接（Handoff）#

资料研究结束后，把当前处理阶段交给值班审核角色。转移记录应包含申请身份、草稿 revision、必要摘要和允许动作，下一条交互才能由正确处理者响应。

这不同于主助手临时调用一个专家。交接后谁接收用户输入、失败时回到哪里、是否允许原角色继续修改，都要在状态中明确。仅输出“请联系值班员”不会改变程序控制权。

路由（Router）#

路由器将“滤镜配置”交给仪器研究，“既往观测记录”交给归档研究，无法分类时进入澄清。输出使用受限类别，保留未知路径，比让字符串任意匹配节点名更可靠。

混合问题可以拆成多个任务，不必强制只能选一位专家。路由测试要包含模糊和不支持的问题，避免未知内容因关键词碰巧匹配而被错误处理。

子 Agent（Subagents）#

主助手保留控制，只委托“核验规则 r1 的开销项”等窄任务。子 Agent 返回引用、限制和完成状态，主助手据此继续计算与审批。

委托合同要说明何时结束以及失败如何返回。若子 Agent 无法访问来源，不能生成一个看似正常的结论来满足格式；主层应能区分缺证据和服务故障。

技能（Skills）#

重复的研究流程可写成技能元数据和正文，需要时加载，不需要每次把全部仪器手册放进 prompt。技能共享的是知识或步骤，不必新增一个持续对话的角色。

共享也带来版本责任。同一流程更新了开销规则，旧申请仍应保留原研究依据。技能加载改变上下文，不应悄悄修改批准状态或获得新增权限。

自定义流程（Custom workflow）#

固定预算节点、仪器子 Agent、归档子图和人工 review 可以组合在同一状态图中。业务确定的顺序由图表达，模型负责适合它的研究与解释。

这种方式适合“不满足预算就不能申请”的约束。无需让多个角色协商一个代码可以直接判断的不等式，也不必为保持纯 Agent 风格隐藏确定性节点。

多 Agent 的记忆边界不变#

委托内部观察保存在子任务范围，父图只接收需要长期保留的结果，待恢复位置由 checkpointer 保存，跨申请偏好或规则索引用 store。角色数量增加不改变这些职责。

应固定共享数据的权威来源。若每个专家都记住一份不同版本的读出开销，再由多数意见决定，会形成难以解释的冲突。可传递资料 ID 与 revision，让专家明确基于哪项记录作结论，而不是复制整段历史。

MCP：让工具连接标准化#

MCP 通过标准交互发现和调用服务暴露的能力，LangChain 的适配包可以把这些能力转为工具对象。它减少连接与协议转换工作，不替应用决定哪些服务可信、哪些能力应对当前用户开放。

接入关注点 天文台场景的问题 应保存或验证的证据
工具发现与转换 服务提供哪些资料查询 工具 schema、名称、描述和变更
连接生命周期 会话是逐调用建立还是长期保持 超时、清理与服务状态依赖
认证 谁在访问远程归档 授权主体、范围、令牌生命周期
执行政策 是否只读、是否允许提交 服务端授权与业务版本核验

下面是适配接口片段，需已安装 langchain-mcp-adapters，并由应用提供审核过的连接配置与模型；它不包含可直接访问的真实服务：

from langchain_mcp_adapters.client import MultiServerMCPClient
from langchain.agents import create_agent

async def make_archive_agent(approved_connections, model):
    client = MultiServerMCPClient(approved_connections)
    discovered = await client.get_tools()
    read_only = [t for t in discovered if t.name in {"archive_lookup"}]
    if not read_only:
        raise RuntimeError("approved archive tool was not discovered")
    return create_agent(model=model, tools=read_only)

实际转换后的工具名可能有前缀或配置差异，应核对发现结果，不照猜名称。需要有状态 MCP 会话时，还应按当前适配包的 session 生命周期使用方式接入，不能假定上述简单工厂保留了任意服务状态。

认证不等于授权，工具描述也属于外部输入。服务更新了描述或返回内容，可能引入不可信指令，应保持资料与系统规则分离。令牌不放入模型 schema 或日志，远程服务返回的执行结果也要按同一工具闭环回填。

协作模式的共同风险#

多数意见不是独立证据#

三位专家都读 SIM-TIME-4@r1 并同意 1500 秒，只能说明同一输入下结论一致。若资料不适用于真实仪器，投票无法纠正适用性问题。

聚合应按来源身份、版本和推断关系整理证据。数值争议可重算，规则争议要回到权威资料或人工核验，不能用角色数量替代独立验证。

部分成功要成为明确的聚合状态#

仪器核验完成、归档服务超时，应保存两项独立状态。产品可以返回带缺项的研究草稿，也可以坚持等待，但不能默认为全部通过。

只重跑失败任务可减少重复费用，合并前仍要检查成功结果是否过期。远程连接恢复不代表先前会话状态仍存在，任务输入需足以安全重建或识别需要重新开始。

失败隔离与预算#

每个子任务、每个远程工具和父图都可能有重试。应计算最坏尝试数，并分配总时长、费用和调用额度；超时后明确降级、终止或请求人工处理。

子任务暂停要让父 UI 可辨认，不能只是一个永不返回的工具调用。版本升级也要带着旧 checkpoint 和连接合同验证，避免图恢复成功但远程工具名称或 schema 已改变。

选型：子图、子 Agent、还是多 Agent 模式#

实际需要改变的部分 合适的起点 需要验证的边界
固定审批与恢复顺序 显式子图或父工作流 状态映射、待恢复任务
独立长研究的上下文 子 Agent 委托 窄输入、结果与预算
问题类型分配 Router 未知、混合与误路由
下一轮由其他处理者接手 Handoff 控制状态与回退
按需补领域流程 Skills 加载范围、版本和可信性
连接外部工具服务 MCP adapters 认证、授权与连接生命周期

这些选择可以并存。先用一个失败场景证明需要哪条边界，再引入相应封装；MCP 不迫使应用采用多 Agent，多 Agent 也不必须通过 MCP 相互通信。

源码入口#

  • 官方 multi-agent/* 页面：对照各模式的控制和上下文关系。
  • 官方 mcp/* 的 tools、connections、auth：核对适配及生命周期合同。
  • langchain-mcp-adapters：按安装版本查看工具转换与客户端实现。
  • deepagents/middleware/：检查委托和技能的实际组合。

先用受控测试服务验证工具发现、拒绝和断连，再考虑真实归档接入。未运行远程连接时，只能描述接入设计，不能把示意配置写成服务已可用的证明。

术语与 API 速查

查术语时可以先写出申请助手中的症状，再找相关对象。比如“拒绝 v1 后仍生成回执”涉及路由与批准版本，“两条资料变四条”涉及增量与 reducer，“关掉进程审批消失”涉及保存实现。名称的用途是定位合同，不是替代运行证据。

本页代码均采用新观测场景。独立可运行的例子使用确定性输入；需要应用已有对象的部分会注明衔接条件。包路径按本书基线与补充文档解释，实际环境仍需核对版本。

名称 在观测申请里的具体含义
Agent 根据已有观察选择下一项工具请求的循环，可因完成或额度而停止
Harness 决定上下文、工具、提示和运行策略的外围组合
Message 带来源和结构字段的交互对象，不能简单替代为显示文字
Tool call 模型提出的动作及参数，尚未代表资源被预留
Runnable 给组件提供单次、异步、批量和增量调用的共同表面
State 某一步可见的申请数据，如资料引用与当前草稿
Partial update 节点这一次产生的变化，如新增两项来源
Reducer 将旧值与更新合成新值的规则，决定追加或其他累计含义
Node 有输入快照和输出更新的工作单元，可以不含模型
Edge 安排后继任务的关系，不是独立数据包传输通道
Super-step 一组任务读取同一前步快照、执行并合并结果的同步步骤
Channel 底层保存值并处理更新的对象，由 schema 等配置映射而来
Checkpoint 定位一个 thread 在某边界的值、版本与后续工作信息
Checkpointer 保存、读取与管理检查点的实现，内存与持久版本保证不同
Store 用 namespace 与 key 组织跨申请可查询数据的接口
Interrupt 将等待外部决定的任务交出，并允许之后恢复
Command 表达更新、跳转或恢复输入的控制对象
Subgraph 可嵌入父流程、有自身状态合同的图
Thread 由 thread_id 寻址的流程实例，不等于用户身份
Deep Agents 将文件、计划、技能和委托等能力预装到标准循环上的组合
Runtime 节点运行时可获得的 context、store 等注入依赖
context_schema 描述单次调用注入依赖的形状，不替代状态 schema
Semantic store search 借 embedding 索引召回相关记录，结果仍需核对版本和范围
langmem 提供摘要与记忆管理相关组件的独立库，需另核对版本
MCP 客户端与外部工具或数据服务交互的标准协议
Handoff 正式改变当前处理角色或控制位置，不只是转述一句话
Event-streaming v3 较新文档描述的统一事件表面，使用前核对目标 API 与版本

工具调用 ID、业务申请号、图 checkpoint ID 和草稿 revision 各有用途。调用 ID 匹配一次请求与观察，业务号关联领域对象，checkpoint ID 定位运行历史，revision 绑定审阅内容。混用它们会使重复请求和旧批准难以辨认。

最小 StateGraph 模板#

这个独立例子把固定申请号与预算组成可执行图，不访问外部服务：

from typing import TypedDict
from langgraph.graph import START, END, StateGraph

class Proposal(TypedDict):
    proposal_id: str
    frames: int
    total_s: int

def budget(state: Proposal):
    return {"total_s": state["frames"] * 200 + 300}

builder = StateGraph(Proposal)
builder.add_node("budget", budget)
builder.add_edge(START, "budget")
builder.add_edge("budget", END)
graph = builder.compile()
result = graph.invoke({"proposal_id": "SIM-QUICK-8", "frames": 8})
assert result["total_s"] == 1900

这里固定每帧 200 秒包含 180 秒曝光与 20 秒读出。真实输入要另做范围校验，不能从 TypedDict 推断所有值已经验证。

带 reducer 的状态#

累计资料时只返回新项，可以用下列纯 Python 计算核对合同：

from operator import add
from typing import Annotated, TypedDict

class Evidence(TypedDict):
    sources: Annotated[list[str], add]

old = ["SIM-REQUEST-1"]
update = ["SIM-TIME-4"]
assert add(old, update) == ["SIM-REQUEST-1", "SIM-TIME-4"]
assert add(old, []) == old

空更新不会清空历史，两个并行列表的顺序也不表示证据权重。需要去重或按来源替换时，应选择相应数据结构和 reducer，而非盲目继续追加。

Checkpointer 模板#

沿用最小模板中的 builder，可观察保存的值与终态：

from langgraph.checkpoint.memory import InMemorySaver

saved_graph = builder.compile(checkpointer=InMemorySaver())
config = {"configurable": {"thread_id": "quick-budget-8"}}
saved_graph.invoke({"proposal_id": "SIM-QUICK-8", "frames": 8}, config)
snapshot = saved_graph.get_state(config)
assert snapshot.values["total_s"] == 1900
assert snapshot.next == ()

新建 saver 或退出进程都会失去这里的内存记录。真实持久性测试必须使用持久实现，并在另一个进程恢复相同地址。

Interrupt 模板#

下面是 review 节点的局部模板，前提是 state 已有稳定草稿、revision，且图绑定 checkpointer。节点后继由应用另行连接：

from langgraph.types import Command, interrupt

def approval(state):
    decision = interrupt({"kind": "proposal.review", "revision": state["revision"],
                          "draft": state["draft"]})
    if type(decision.get("approved")) is not bool:
        raise ValueError("expected a boolean decision")
    if decision.get("revision") != state["revision"]:
        raise ValueError("decision is for another revision")
    return {"approved": decision["approved"]}

# 首次 invoke 暂停后，使用原 thread 配置恢复动态中断。
resume_input = Command(resume={"approved": False, "revision": 1})

它只演示动态恢复值，不调用远程服务。静态 interrupt_before 断点通常通过 None 继续，不能照搬这份业务决定；中断前的代码也必须允许重放。

事实强度#

遇到争议时，优先检查同版本源码与测试是否直接体现该行为，再核对公开文档承诺。官方博客可解释设计动机，本书的工程建议则说明适用条件和风险，不提升为框架自动保证。

教学推演需要给出输入、规则和状态结果，但不等于实测服务。比如 8 帧得到 1900 秒可由本地公式验证，真实观测质量、吞吐和沙箱隔离则需要另行实验。embedding 召回排序也不构成事实可信度证明。

同样，离线回归通过只覆盖执行过的断言。它不能证明并发恢复、所有 provider 或未来版本都兼容。报告结果时应连同解释器、包版本和测试入口一起保留，便于复现。

核心讲解以 langchain 1.4.2、langchain-core 1.6.4、langgraph 1.2.12 与 langgraph-checkpoint 4.2.0 的快照关系为基线。实际运行其他版本时，应先核对依赖和关键签名；成功 import 只能说明入口存在，不能证明所有语义不变。

deepagents、langmem 和 langchain-mcp-adapters 属于独立发布的包。章节讨论其职责与接入边界，示意片段若没有完整依赖与服务配置，会明确说明前提，不把它们算作两个离线 CLI 已验证的功能。
